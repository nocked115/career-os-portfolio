## 1. Opportunities 가 하는 일

채용공고만 보는 게 아니다.

```
Jobs            채용공고
Internships     인턴십
Competitions    공모전
Activities      대외활동
```

그리고 목적은 **많이 가져오는 것이 아니라 선별하는 것**이다.

```
❌ "관련 공고 47건을 찾았습니다."
✅ "지금 할 만한 건 2건입니다. 나머지는 지금은 아닙니다."
```

## 2. 수집 — Source Adapter

Career OS 는 **하나의 채용 플랫폼에 종속되면 안 된다.**

```
외부 소스 → fetch() → normalize() → Opportunity → Career OS
```

### 어댑터 계약

수집원은 네 가지만 노출한다.

```python
SOURCE_NAME: str
is_available() -> bool      # 자격 증명이 있는지 등
fetch() -> list[dict]       # 원본 그대로
normalize(raw) -> dict      # base.normalize_opportunity() 사용
```

레지스트리에 등록하면 끝이다.
**비즈니스 로직은 어떤 소스가 있는지 알지 못한다.**

테스트가 레지스트리 전체를 돌며 계약을 검사하므로,
소스를 추가해도 형태가 조용히 깨지지 않는다.

### 정규화 규칙

```
필수          source · title
없으면 비운다  organization · role · location · deadline
추측하지 않는다  해석 못 하는 마감일은 None. 임의의 날짜를 만들지 않는다
원본 보존      raw_payload 에 원본을 남긴다
```

### 중복 처리

```
(source, source_external_id) 로 판단

이미 있으면    제목 · 설명 · 마감일 등을 갱신
              단, 사용자가 바꾼 status 는 덮어쓰지 않는다
없으면        새로 만든다
```

### 레거시 Job 병행

```
Job              대시보드와 /jobs/{id}/match 가 아직 이걸 본다
  ▲
  │ legacy_job_id (1:1, nullable)
  │
Opportunity      수집기가 쓰는 곳
```

`opportunity_type == "job"` 인 기회는 레거시 `Job` 도 만들어 연결한다.
이행 구조이므로 언제 끝낼지는 Phase 1 에서 정한다.

### 연결하고 싶은 소스

사용자가 원하는 대상은 다음과 같다. 종류별로 성격이 다르다.

**채용 · 인턴**

```
워크넷 / 고용24        공공데이터포털에 공식 API 가 있고 약관이 명확하다
사람인                 공식 API 신청함. 승인 대기 중
원티드                 공식 API 유무와 조건을 확인해야 한다
잡코리아               공식 API 유무와 약관을 확인해야 한다
```

**공모전 · 대외활동** — 이쪽 물량은 채용 사이트가 아니라 여기에 있다

```
링커리어 (Linkareer)
캠퍼스픽 (Campuspick)
```

### 소스를 추가하기 전에 확인할 것

각 소스마다 이 세 가지를 먼저 확인한다. **추측하지 않는다.**

```
1. 공식 API 가 있는가        있으면 그것만 쓴다
2. robots.txt 가 허용하는가
3. 이용약관의 자동수집 조항
```

**주요 취업 사이트는 대부분 약관에서 자동 수집을 금지한다.**
확인 결과 막혀 있으면 그 소스는 붙이지 않는다.
어댑터 구조는 소스를 쉽게 붙이기 위한 것이지,
붙여도 되는지를 판단해주지는 않는다.

### 막혀 있을 때의 대안

```
붙여넣어 가져오기  사람이 읽은 공고 본문을 붙여넣으면 칸을 채운 미리보기를 준다 (아래).
               지금 화면의 기본 경로다
수동 등록      POST /opportunities 로 관심 공고를 직접 넣는다.
               source 가 manual 이면 상태를 interested 로 시작한다
기업 채용 페이지  개별 기업 페이지는 상대적으로 허용 범위가 넓고
               RSS 나 JSON 을 열어둔 곳도 있다. 사이트마다 확인한다
```

### 지켜야 할 것

> **각 소스의 약관과 허용된 접근 방식을 먼저 확인한다.**
> 모든 사이트를 스크래핑할 수 있다고 가정하지 않는다.
> 실제 외부 연동은 Phase 7 이다.

**스크래핑은 하지 않는다. 일부러다.** 앱은 공고 사이트를 열지 않는다 —
붙여넣기에서 받은 링크도 저장만 하고 열지 않는다.

등록된 수집원은 `mock` 과 `saramin` 둘이다 (`collectors/__init__.py` `REGISTRY`).
`saramin` 은 사람인 공식 API 어댑터이고, **키가 있고 공개 데모가 아닐 때만**
동작한다(`is_available`) — 공개 데모에 사람인 공고를 싣는 것은 약관의 재배포
금지에 걸린다. 어댑터 하나는 파일 하나이므로, 확인이 끝난 소스부터 붙이면 된다.

### 붙여넣어 가져오기 — `POST /opportunities/parse`

규칙 기반이다 (`services/posting_parser.py`). LLM 도, 외부 요청도 없다.

```
입력      text(붙여넣은 본문) · url(선택 — 저장만 하고 열지 않는다)
출력      미리보기. 저장하지 않는다. 틀린 칸은 사람이 고치고
          POST /opportunities 로 저장한다 (description 에 본문 그대로)
```

| 칸 | 찾는 법 | 못 찾으면 |
|---|---|---|
| 제목 | 앞 15줄에서 `채용 · 모집 · 공고 · 인턴` → 없으면 `부문 · 직무 · Engineer …` | 비우고 note |
| 기관 | `회사명: …` 같은 라벨 → 앞 20줄의 `㈜ · (주) · 주식회사` | 비우고 "직접 넣어 주세요" |
| 종류 | `공모전 · 경진대회 · 해커톤` / `대외활동 · 서포터즈 …` | job 으로 보고 found=false |
| 고용 형태 · 근무지 | 정해진 표현 · 라벨 | 비운다 |
| 마감 | `마감 · 접수기간 · ~` 가 있는 줄의 날짜. 기간이면 끝나는 날 | 상시 · 수시면 rolling, 아니면 비운다 |
| 요구 스킬 | 등록된 스킬 이름을 본문에서 찾는다 (`jd.extract_skills`) | 경고 — 분모만 늘어난다 |
| 지원 자격 | `지원자격 · 자격요건 · 우대사항 …` 머리글 아래, 다음 섹션까지 최대 15줄 | 경고 — 원문에서 확인하라 |

**못 찾으면 비워 둔다.** 날짜와 회사를 짐작해서 채우지 않는다. 찾은 칸마다
근거가 된 줄(`evidence`)을 같이 돌려주고, 짐작한 부분은 `note` 로 밝힌다 —
"연도가 없어 2026년으로 봤어요" · "시각이 없어 23:59 로 봤어요".

### 자격 경고 — `requirement_flags`

매칭 점수만 보고 "학계 1년 이상" 같은 요건을 놓친 일이 있었다. 그래서
걸림돌이 될 수 있는 표현이 있는 **줄**을 따로 표시한다.

```
career     경력 요건          N년 이상 · 경력 N년 · 경력자 · 학계 · 실무 경력
degree     학력 · 졸업 요건   석사 · 박사 · 학위 · 졸업 예정 · 졸업자
language   어학 요건          OPIc · 토익 · TOEIC · TOEFL · IELTS · 어학 …
license    자격증 요건        자격증 필수/소지 · 기사 자격 · 자격 소지
```

자격 머리글 아래를 먼저 보고, 머리글이 없으면 글 전체를 본다.
**충족하는지는 판단하지 않는다** — 문장을 찾아 눈에 띄게 할 뿐이다. 붙여넣기
미리보기와, 저장된 기회의 채점 결과(`requirement_flags`, 본문에서 다시 찾는다)에
둘 다 들어간다.

### 경고 옆의 내 어학 · 자격 — `my_certificates`

경고만 있으면 "그래서 나는?" 을 다른 화면에서 찾아야 한다. 그래서 경고 옆에
내가 **보유**로 등록한 자격을 나란히 둔다 (`certificates.relevant`).

```
language 경고   → 내 어학       (예: OPIc IH · TOEIC 900 (만료 120일 전))
license 경고    → 내 직무 자격
career · degree → 붙이지 않는다
```

만료됐거나 180일 안에 만료되면 옆에 적는다. 등록한 것이 없으면
"등록한 것이 없어요 — 추가하기" 로 경험 화면의 자격 칸으로 보낸다.
여기서도 충족 여부는 판단하지 않는다.

## 3. 매칭 — "이걸 지금 하는 게 가치가 있는가"

### 점수 구성 — 100점

| 요소 | 배점 | 판단 |
|---|---|---|
| **관련성** | 40 | 지금 우선순위가 높은 스킬을 요구하는가 (1위 스킬 대비 상대값) |
| **준비도** | 30 | 요구 스킬 중 이미 보유한 비율 |
| **포트폴리오 가치** | 15 | 공모전·대외활동이거나, 증거 없는 스킬을 요구하는가 |
| **마감 실현 가능성** | 15 | 남은 일수 (7일 미만 촉박 · 30일 이상 여유) |

### 판정

```
70점 이상   recommended
40 ~ 69     consider
40점 미만   skip
마감 지남   점수와 무관하게 skip
```

### 설명 가능해야 한다

**설명할 수 없으면 추천하지 않는다.**

```
[83] recommended   AI 데이터 분석 공모전   D-43

· 지금 우선순위가 높은 스킬을 요구합니다: Python.
· 요구 스킬 1개 중 1개를 보유하고 있습니다.
· 결과물이 포트폴리오 증거로 남습니다.
· 마감까지 43일 남았습니다.
```

### "Skip this" 도 1급 시민이다

숨기지 않고 이유와 함께 말한다.

```
[24] skip   백엔드 인턴   D-5

· 지금 우선순위가 높은 스킬과는 겹치지 않습니다.
· 요구 스킬 5개 중 1개를 보유하고 있습니다.
· 마감까지 5일뿐이라 촉박합니다.
· 지금은 다른 것을 먼저 하는 편이 낫습니다.
```

### 추천이 없으면 빈 목록

억지로 채우지 않는다. 할 만한 게 없다는 것도 유효한 답이다.

### 필요 시간 (Phase 3)

남은 날짜만으로는 "할 수 있는가" 를 판단할 수 없다.
**40시간짜리를 5일 안에** 와 **4시간짜리를 5일 안에** 는 다르다.

`Opportunity.estimated_hours` 를 알면 하루에 몇 시간을 써야 하는지로 판단한다.

```
하루 1시간 이하   comfortable
하루 2시간 이하   workable
하루 4시간 이하   tight        "빠듯합니다"
하루 4시간 초과   unrealistic  "지금 일정으로는 끝내기 어렵습니다"
```

필요 시간을 모르면 예전처럼 남은 날짜만으로 판단한다.
모르는 걸 추정해서 넣지 않는다.

### 목표 직무 관련성 (Phase 1 에서 해결됨)

관련성 항목이 학습 우선순위를 읽고, 학습 우선순위가 Target Career 를
반영하므로 **별도 구현 없이 따라왔다.** 단일 출처의 이점이다.

## 4. Market Signals

수집된 실제 데이터에서만 계산한다.

### 현재 수요

```
opportunity_count   이 스킬을 요구하는 기회 수
percentage          전체 기회 대비 비율
```

### 추세

시점별 값이 없으면 "올랐다/내렸다" 를 말할 수 없다.
수집이 끝날 때마다 스킬별 수요를 `MarketSnapshot` 에 한 줄씩 남기고,
가장 최근 두 스냅샷을 비교한다.

```
up        3포인트 이상 상승
down      3포인트 이상 하락
flat      3포인트 미만 변화
unknown   비교할 과거가 없음
```

### 규칙

```
✅ 스냅샷이 하나뿐이면 unknown 이다. 화살표를 그리지 않는다
✅ 데이터가 부족하면 부족하다고 표시한다
❌ "AWS 는 요즘 인기입니다" 같은 근거 없는 문장
❌ 그럴듯한 퍼센트를 만들어내기
```

구현 주의: 순서는 `captured_at` 이 아니라 id 기준이다.
SQLite 의 `CURRENT_TIMESTAMP` 는 초 단위라
같은 초에 저장된 스냅샷을 시간으로 구분할 수 없다.

## 5. 화면 — 기회

사이드바 `기회` (`OpportunitiesPage.jsx`). 많이 보여주는 곳이 아니라 **어떤 것을
고를지 돕는 곳**이다.

```
기회                                   [+ 공고 붙여넣기] [수집 실행]
어떤 기회를 고를지 근거와 함께 판단합니다.
┌ ◇ 채용 · 인턴 · D-23 ──────────────────────────────────────────┐
│ 지원할지 정하기 — Data Scientist Intern                           │
│ 매칭 73/100 · 요구 스킬 3개 중 2개 보유 · ⚠ 자격 확인 필요         │
│                                [ 지원서 만들기 ] [ 근거 보기 ]    │
└──────────────────────────────────────────────────────────────────┘

[검토 중 3] [보류 0] [관심 없음 0] [전체 3]
[모든 종류] [채용 · 인턴] [공모전] [대외활동]

AI 데이터 분석 공모전        84/100  D-43  │ 공모전
Mock Data Association · 공모전             │ AI 데이터 분석 공모전     84 / 100 매칭
Data Scientist Intern        73/100  D-23  │ [지금 할 만해요] [공고 원문 ↗]
… · 채용 · 인턴  [자격 확인]               │ 이 기회를 고려할 이유
지금은 아닌 것 · 1건                        │  · 지금 우선순위가 높은 스킬을 요구합니다: Python.
 우선순위가 낮거나 마감이 지나 아래로 …     │ 필요한 역량 · 나와의 연결   ✓ Python  ! SQL
백엔드 인턴                  24/100  D-5   │ ⚠ 지원 자격을 확인하세요
                                           │  어학 요건  TOEIC 800 이상
                                           │  내 어학    TOEIC 900
                                           │ 예상 준비 비용  약 40시간 · 마감까지 하루 1시간
                                           │ 마감            D-43 · 여유 있음
                                           │ ▸ 매칭 점수 구성 보기
                                           │ 다음 행동
                                           │ [지원서 만들기] [오늘 계획에 준비 추가]
                                           │ [지금은 보류] [관심 없음]

(아래) 이 공고 기준 지도 — 스킬 → 공부 → 프로젝트 → 경험
시장 신호 · 모아둔 기회 기준 — 스킬별 N / 전체 건 · % · 추세
```

| 화면 말 | 서버 값 |
|---|---|
| 지금 할 만해요 · 고려해 볼 만해요 · 지금은 아니에요 | `recommended · consider · skip` |
| 여유 있음 · 할 만함 · 빠듯함 · 지금 일정으로는 어려움 · 마감 지남 · 마감일 없음 | `deadline_state` |
| 검토 중 · 보류 · 관심 없음 · 전체 | `status` 로 거른다. 검토 중은 `on_hold · not_interested · closed` 를 뺀 것 |

**맨 위 카드는 하나다.** 검토 중이고, skip 이 아니고, 아직 지원서가 없고,
마감이 안 지난 것 중 마감이 가장 가까운(같으면 점수 높은) 기회. 없으면
"지금 새로 판단할 기회가 없어요" 라고 쓴다.

**`지금은 아닌 것` 은 숨기지 않고 목록 안에 둔다.** 평가가 아니라 오늘의
집중을 지키려고 아래로 내렸다는 뜻이다. **보류와 관심 없음은 사용자가 정한다**
(`PATCH /opportunities/{id}` 의 `status`). 옮기면 오늘 마감 띠와 계획에서 빠지고
해당 칸으로 간다. `다시 검토하기` 로 되돌린다.

매칭 점수 구성은 접어두고, 펼치면 네 칸(40 · 30 · 15 · 15)과 판정 기준을 보인다.

### 계획에 추가 (Phase 3)

`POST /opportunities/{id}/add-to-plan`

기회를 보고 "할 만하다" 고 판단했으면 오늘 계획으로 이어져야 한다.
여기서 끊기면 DISCOVER 가 북마크 목록으로 끝난다.

```
지원서가 없으면 관심(interested) 상태로 하나 만든다
        ↓
오늘 계획에 "지원 준비 — {제목}" 태스크를 올린다
```

지원서를 함께 만드는 이유는, 기회만 계획에 넣으면
나중에 "이거 어떻게 됐더라" 를 추적할 곳이 없기 때문이다.
이미 지원서가 있으면 그것을 쓰고 **사용자가 정한 상태를 덮어쓰지 않는다.**
같은 기회를 두 번 추가해도 중복되지 않는다 (`already_planned`).
응답의 `created_application` 으로 화면이 "지원서도 관심 상태로 만들었어요" 를
덧붙인다. 기본 30분, 5~480분.

화면 버튼 이름은 `오늘 계획에 준비 추가` 다. `지원서 만들기` 는 계획 없이 지원서만
만들고, 지원서가 있으면 `지원서 열기 · {상태}` 로 바뀌어 Workspace 로 간다
→ [APPLICATIONS.md](APPLICATIONS.md)

## 6. Job Analysis

지원서를 열면 JD 를 분석한다 (`services/jd.py` `analyze_application`,
화면은 Workspace 의 `JD 분석 · 요구 역량`).

### 지금 되는 것 (2026-09-15 확인)

```
✅ JD 본문에서 등록된 스킬 이름 · 별칭을 찾는다. 본문에서 못 찾으면 공고에 직접 연결한 스킬로 본다 (basis: linked)
✅ 단어 경계를 지킨다 — "Go" 가 "Google" 에, "C" 가 "CSS" 에 걸리지 않는다.
   한글 이름은 조사까지만 허용한다
✅ 강도를 나눈다 — 레벨 3 이상 strong · 1 이상 medium · 0 gap
✅ 매칭은 본문에 자주 · 앞쪽에 나온 역량에 가중치를 준 비율 (match_score)
✅ 요구 역량을 덮는 Experience 를 점수와 함께 추천한다 (recommend_experiences)
```

### 아직 한계 — 정직하게

```
❌ 등록된 스킬의 이름과 별칭(aliases)만 찾는다. 스킬 목록에 없는 요구 역량은 보이지 않는다
❌ 문맥을 읽지 않는다. "우대" 와 "필수" 를 구분하지 않는다
❌ 화면의 보유 판정은 레벨 1 이상이다 — strong / medium 구분은 화면에 드러나지 않는다 (레벨 숫자만 쓴다)
```
