# 배포

앱은 **컨테이너 하나**다. 화면과 API 를 같은 서비스가 낸다.
둘로 나누면 CORS, 두 개의 URL, 두 번의 배포가 생기는데
1인용 앱에 그럴 이유가 없다.

---

## 1. 무엇을 올릴지 먼저 정한다

**배포본은 로컬과 다른 DB 를 쓴다.** 같은 DB 를 쓸 방법은 없다 —
로컬은 `backend/career_os.db` 파일이고, 배포본은 컨테이너 볼륨이다.

| | 넣는 데이터 | 쓸 수 있나 | 누가 보나 |
|---|---|---|---|
| **실사용** | 진짜 공고·일정·프로필 | 어디서나 | 나만 (Basic Auth) |
| **데모** | 가짜 데이터 | 쓰기 차단 | 링크 아는 누구나 (인증 없음 · 8장) |

포트폴리오로 보여줄 거면 **데모용을 따로 하나 더** 띄우는 게 낫다.
실사용 배포본의 비밀번호를 남에게 주면 그때부터 실제 지원 내역이
공개된다.

---

## 2. 환경변수

| 변수 | 필수 | 설명 |
|---|---|---|
| `CAREER_OS_ENV` | | `Dockerfile` 이 `production` 으로 이미 넣어 둔다 |
| `CAREER_OS_AUTH_USER` | ✅ | Basic Auth 사용자명 (공개 데모면 불필요) |
| `CAREER_OS_AUTH_PASSWORD` | ✅ | Basic Auth 비밀번호. **길게** (공개 데모면 불필요) |
| `CAREER_OS_DATABASE_URL` | | 컨테이너 기본 `sqlite:////data/career_os.db` |
| `PORT` | | 호스트가 준다. 기본 8000 |
| `CAREER_OS_READ_ONLY` | | 켜면 쓰기 차단 (8장) |
| `CAREER_OS_PUBLIC_DEMO` | | 켜면 인증 없음 + 쓰기 차단 (8장). **실사용 금지** |
| `CAREER_OS_SEED_DEMO` | | `1` 이면 DB 가 비어 있을 때 데모 데이터를 채운다. **실사용 금지** |
| `SARAMIN_API_KEY` · `CAREER_OS_SARAMIN_KEYWORDS` | | 공고 수집원 (9장) |

**`CAREER_OS_ENV=production` 인데 자격 증명이 없으면 앱이 아예 뜨지
않는다** (`auth.check_startup`). 예외는 공개 데모뿐이다. 기본 비밀번호를 두면 그게 곧 공개 배포이기 때문이다.
조용히 인증을 끄는 것보다 배포가 실패하는 편이 낫다.

비밀번호는 이렇게 만든다.

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(24))"
```

## 3. 볼륨

**`/data` 를 영속 볼륨으로 잡아야 한다.** 안 잡으면 컨테이너를 다시
띄울 때마다 모든 데이터가 사라진다. 지원 내역도, 캘린더도.

호스트마다 이름이 다르다 — Railway `Volume`, Render `Disk`,
Fly.io `fly volumes create`.

데모는 예외다. `CAREER_OS_SEED_DEMO=1` 이면 뜰 때마다 빈 DB 를 다시
채우므로 볼륨 없이도 된다. `Dockerfile` 이 `/data` 를 미리 만들어 두어
볼륨이 없어도 DB 파일을 열 수 있다.

---

## 4. 올리기

```bash
# 저장소 루트에서
docker build -t career-os .

docker run -p 8000:8000 \
  -e CAREER_OS_ENV=production \
  -e CAREER_OS_AUTH_USER=... \
  -e CAREER_OS_AUTH_PASSWORD=... \
  -v career-os-data:/data \
  career-os
```

호스트에 올릴 때는 저장소를 연결하고 위 환경변수와 볼륨만 맞추면
된다. `Dockerfile` 이 알아서 화면을 빌드하고, 뜰 때 마이그레이션을
돌린다(`alembic upgrade head`).

---

## 5. 확인

```bash
curl -i https://<주소>/            # 401 · WWW-Authenticate 있어야 함
curl -i https://<주소>/healthz     # 200 · 인증 없이 열려 있음
curl -u user:pass https://<주소>/  # 200 · HTML
```

`/healthz` 만 인증 없이 연다. 로드밸런서 헬스체크가 401 을 받으면
배포가 계속 실패한 것으로 보이기 때문이다.
(공개 데모는 인증이 없으므로 `/` 도 바로 200 이다.)

## 6. 알아둘 것

**Basic Auth 의 한계.** 이 앱에는 사용자 모델도 세션도 없다.
인증은 "이 배포본에 접근할 수 있는가" 하나만 판단한다.

- **HTTPS 는 필수다.** Basic Auth 는 요청마다 자격 증명을 보낸다.
  평문 HTTP 로 띄우면 그대로 노출된다. 대부분의 호스트가 HTTPS 를
  기본으로 주지만, 직접 띄운다면 반드시 확인할 것.
- 로그인 시도 제한이 없다. 비밀번호를 길게 쓰는 것이 유일한 방어다.
- 호스트 운영자는 볼륨의 DB 를 볼 수 있다. 그게 곤란한 데이터라면
  배포하지 않는 편이 낫다.

**SQLite 를 쓴다.** 1인용이라 충분하다. 다만 여러 인스턴스로
늘리면 깨진다. `CAREER_OS_DATABASE_URL` 로 주소는 바꿀 수 있지만
PostgreSQL 로 **그냥 옮겨지지는 않는다** — 드라이버가
`requirements.txt` 에 없고, 불러오기 뒤 시퀀스(`setval`) 보정도
없다 (`services/transfer.py` 의 주석).

**로컬 개발은 그대로다.** 인증은 자격 증명 두 변수가 **둘 다 있을
때만** 켜진다 — 로컬에서 비워 두면 꺼진다. `CAREER_OS_ENV` 는 켜고
끄는 스위치가 아니라, `production` 일 때 자격 증명이 없으면 기동을
막는 검사다. `backend/static` 이 없으면 API 만 낸다.
화면은 `npm run dev` 가 따로 낸다.

## 7. 데이터 옮기기 · 백업

배포본의 DB 는 볼륨 안의 SQLite 파일 하나다. 밖에서 만질 수 없다.
그래서 넣는 길도 꺼내는 길도 API 하나뿐이다.

```
GET  /transfer/export                     현재 DB 를 통째로 JSON 으로
POST /transfer/import?confirm=REPLACE     그 JSON 으로 통째로 대체
```

둘 다 다른 경로와 똑같이 Basic Auth 에 막힌다.

### 로컬 → 배포본

```bash
# 1. 로컬 서버를 띄운 상태에서 뽑는다
curl -s http://localhost:8000/transfer/export > career-os-backup.json

# 2. 배포본에 넣는다
curl -u '<아이디>:<비밀번호>' \
  -X POST 'https://<주소>/transfer/import?confirm=REPLACE' \
  -H 'Content-Type: application/json' \
  --data-binary @career-os-backup.json
```

응답에 테이블별 행 수가 나온다 — `replaced`(지우기 전에 있던 행),
`written`(넣은 행), `kept`(남긴 행, 아래 참고). 엉뚱한 서버에
쐈다면 `replaced` 를 보고 바로 알 수 있다.

### 배포본 → 로컬 (백업)

같은 `export` 를 배포본에 쏘면 된다. 이게 유일한 백업 경로다.

```bash
curl -u '<아이디>:<비밀번호>' \
  https://<주소>/transfer/export > career-os-backup-$(date +%F).json
```

### 방향을 헷갈리지 말 것

DB 는 두 개고 **서로를 모른다.**

```
로컬     backend/career_os.db            개발하면서 고치는 곳
배포본   Railway 볼륨 /data/career_os.db   실제로 쓰는 곳
```

배포본을 실제로 쓰기 시작했다면 **배포본이 원본이다.** 거기서 챕터를
완료하고 레벨을 올린 뒤 그 전에 뜬 로컬 파일을 올리면, 그 작업이
통째로 사라진다.

**순서는 항상 이렇다.**

```
1. 배포본에서 받아온다   export  →  career-os-backup.json
2. 로컬에서 고친다
3. 배포본으로 올린다     import
```

받아오지 않고 2번부터 시작하면 안 된다.

**서버가 막아준다.** 파일이 받는 쪽의 작업을 담고 있지 않으면
`import` 가 **409** 로 거부한다.

```json
{"detail": "받는 쪽에 이 파일에 없는 작업이 있습니다
  (파일 2026-09-10 11:38, 서버 2026-09-12 21:04).
  그대로 올리면 그 작업이 사라집니다. 먼저 서버에서 export 로 받아오세요."}
```

**무엇과 무엇을 비교하는지가 이 검사의 전부다.** 파일이 *언제 떴는지*
(`exported_at`)가 아니라 **파일 안의 마지막 작업**과 서버의 마지막
작업을 잰다. 뜬 시각으로 재면 한 번 통과한다 — 배포본에서 14:30 에
한 일이 있는데 로컬에서 14:40 에 뜬 파일이면 "최신" 으로 보인다.
파일을 언제 떴는지는 그 파일이 저쪽 작업을 담고 있는지와 무관하다.

정말 덮어써야 한다면 `&allow_stale=true` 를 붙인다. 그 작업은
사라지고 되돌릴 수 없다.

무엇을 "작업" 으로 세는지: 완료한 태스크·챕터·학습 단계, 레벨 변화,
경험·포트폴리오·지원의 수정. **스케줄러가 매일 건드리는 것은 세지
않는다** — 그것까지 세면 아무것도 안 해도 항상 경고가 뜨고, 경고가
늑대 소년이 된다.

### 알아둘 것

- **합치지 않는다. 대체한다.** 불러오기는 기존 데이터를 전부 지운다.
  합치면 같은 ID 를 가진 다른 레코드가 부딪히고, 무엇이 남았는지
  아무도 모르게 된다. 그래서 `confirm=REPLACE` 없이는 실행되지 않는다
  (없으면 400).
  예외 하나: 스케줄러가 매일 쌓는 `market_snapshots` 는 파일에 없는 줄을
  지우지 않고 남긴다 (응답의 `kept`). 대체하면 서버에서 쌓인 날들이
  사라지기 때문이다.
- **스키마 리비전이 다르면 거부한다 (400).** 내보낸 파일의
  `schema_revision` 과 받는 쪽 `alembic_version` 이 같아야 한다.
  컨테이너는 뜰 때 `alembic upgrade head` 를 돌리므로, 로컬도
  `alembic upgrade head` 로 같은 head 에 맞춘 뒤 다시 뜬다. 컬럼 하나가
  조용히 빠진 채 들어가는 것이 더 나쁘다. (`allow_schema_mismatch=true`
  로 검사를 끌 수 있지만, 바로 그 위험을 떠안는다.)
- **내보낸 파일은 진짜 경력 기록이다.** `.gitignore` 가 저장소
  최상단의 `career-os-*.json` 과 어디서든 `*.career-os.json` 을
  막아두었지만, 다른 이름이나 다른 폴더에 저장했다면 직접 챙길 것.
- 데모 배포본에 불러오기를 쏘면 안 된다. 데모는 가짜 데이터만 있는
  공개용이다.

## 8. 데모를 링크 하나로 여는 법

포트폴리오 데모에 비밀번호를 걸면, 링크를 연 사람이 README 로
돌아가 아이디를 옮겨 쳐야 한다. 거기서 대부분 이탈한다. 데모
데이터는 전부 지어낸 것이라 숨길 것도 없다.

```
CAREER_OS_PUBLIC_DEMO=1
```

이 변수가 있으면:

- 자격 증명 없이도 뜬다 (운영 환경의 기동 검사를 통과한다)
- **쓰기가 강제로 막힌다.** `is_read_only()` 가 참이 되어
  POST/PUT/PATCH/DELETE 가 전부 403 이다.

"공개인데 쓰기 가능" 이라는 상태는 만들 수 없다. 그게 가능하면
링크를 아는 누구나 `/transfer/import` 한 번으로 데모를 비운다.

### 절대 실사용 배포에 넣지 말 것

이 변수 하나가 진짜 경력 기록을 인증 없이 공개한다.
`CAREER_OS_READ_ONLY` 와 이름을 나눈 이유가 그것이다 — 이름만
보고도 무슨 일이 벌어지는지 알아야 한다.

기동 로그가 모드를 그대로 적는다. 실사용 배포에서 이 줄이 보이면
즉시 변수를 지울 것.

```
[Career OS] 공개 데모 모드 — 인증 없음, 쓰기 차단.
```

### 정리

| 변수 | 인증 | 쓰기 | 쓰는 곳 |
|---|---|---|---|
| (없음) | 필요 | 가능 | 실사용 |
| `CAREER_OS_READ_ONLY=1` | 필요 | 차단 | 아는 사람에게만 보여줄 때 |
| `CAREER_OS_PUBLIC_DEMO=1` | **없음** | 차단 | 포트폴리오 데모 |

## 9. 공고 수집원

스케줄러가 매일 08:00(서버 시간대 기준 — 코드에 시간대 지정이 없다)에
켜진 수집원을 모두 돌린다. **공식 API 가 있는
곳만 연결한다.** 스크래핑하지 않는다.

| 수집원 | 켜지는 조건 | 비고 |
|---|---|---|
| mock | 운영이 아닐 때만 | 운영에서 돌면 가짜 공고가 수요 분모에 섞인다 |
| 사람인 | `SARAMIN_API_KEY` 가 있고 공개 데모가 아닐 때 | 하루 500회 · 출처 표시 의무 · 재배포 금지 |

```
SARAMIN_API_KEY=...                         # oapi.saramin.co.kr 에서 승인 후 발급
CAREER_OS_SARAMIN_KEYWORDS=데이터 분석,머신러닝,인공지능   # 키워드마다 1회 호출
```

**사람인 키는 신청 후 승인이 나야 나온다.** 승인 전에는 로그인 화면에
"사용승인이 되지 않은 사용자" 가 뜬다. `SARAMIN_API_KEY=` 처럼 값이 비어
있으면 꺼진 것으로 본다.

**사람인 응답에는 공고 본문이 없다.** 직무명·키워드·경력만 온다. 그걸로
스킬을 찾으므로 손으로 넣은 공고보다 연결이 얕다. 마감일은
`close-type` 이 "접수 마감일" 일 때만 넣는다 — 상시·수시 공고에 만료
시각을 마감으로 넣으면 가짜 D-day 가 뜬다.

**모인 공고는 `discovered` 로 들어간다.** 마감 추적과 오늘 계획은
`interested` 부터 본다. 매일 수십 건이 들어와도 오늘 계획이 공고로
뒤덮이지 않는다 — 수요 계산에만 들어가고, 지원할 것은 사람이 고른다.
