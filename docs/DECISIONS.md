# 무엇을 정했고, 무엇을 포기했는가

Career OS 를 만들면서 내린 결정들의 기록.

DESIGN.md 는 **무엇을 만들지**를 고정하고, SPEC.md 는 **어떻게 도는지**를
적는다. 이 문서는 **왜 그렇게 정했고 그 대가로 무엇을 포기했는지**를 남긴다.
결정만 남기고 이유를 버리면, 반년 뒤에 같은 자리를 다시 판다.

기간: 2026-08-09 ~ 2026-09-15 · 커밋 90개

---

## 0. 북극성

> **"오늘 뭘 하면 되지?"**

이 문장 하나가 모든 결정의 판정 기준이었다. 어떤 기능이 이 질문에
답하지 못하면 넣지 않았다.

세 원칙이 여기서 나왔다.

| 원칙 | 뜻 |
|---|---|
| 근거 없는 추천은 없다 | 모든 숫자는 셀 수 있는 것에서 나온다 |
| 안 해도 되는 것을 말한다 | 라이브러리는 고르는 곳이지 쌓는 곳이 아니다 |
| 홈은 특별하게, 작업 화면은 편하게 | 우주는 홈에만. 일하는 화면은 평범하게 |

## 1. 대시보드가 아니라 판단

**문제.** 커리어 관련 도구는 대부분 숫자를 보여주고 해석을 사용자에게
떠넘긴다. "지원 12건, 서류 통과 3건" 을 보여준 다음, 그래서 오늘 뭘
할지는 사용자가 알아서 정하라고 한다.

**정한 것.** Career OS 는 **판단을 하고, 그 판단의 근거를 같이 낸다.**
Today 화면은 오늘 할 일 세 개를 정해서 내놓고, `Why this plan?` 은 그
셋이 왜 그것인지를 여덟 개 입력으로 펼친다.

**대가.** 판단이 틀리면 도구가 통째로 신뢰를 잃는다. 대시보드는 틀릴
일이 없다 — 숫자만 보여주니까. 이 선택은 계산이 정직해야만 성립한다.
아래 결정들 대부분이 그 정직함을 지키는 일이었다.

## 2. 학습 우선순위와 실행 우선순위를 나눈다

**문제.** 외부 검토에서 나온 지적이었다.

> "핵심 계산에서 '학습 우선순위'와 '실행 우선순위'를 하나의 숫자로
> 섞고 있는 게 지금 가장 큰 설계 문제라고 본다."

**확인해보니 절반은 이미 되어 있었다.** `priority.py` 가 1층(무엇을
배울 것인가), `today.py` 가 2층(그래서 오늘 뭘 할 것인가)이었다.
지적이 가리킨 추상적 문제는 이미 분리돼 있었다.

**진짜 결함은 더 좁고 더 나빴다.** 2층의 `build_candidates` 가
`entries[0]` 만 읽고 있었다. 그래서 프로젝트를 하나 붙이면 그 스킬이
1위에서 밀리고, **밀리는 순간 그 프로젝트 자체가 오늘 계획에서
사라졌다.** 60% 진행 중인 프로젝트로 재현했다.

**정한 것.** 프로젝트를 스킬 순위에 종속시키지 않고 **자기 자격으로
후보**가 되게 했다 (커밋 `bfe7693`). 마감 → 진행률 → 필요도 순으로
정렬하고 최대 2개까지.

**배운 것.** 추상적인 지적을 그대로 받아 적으면 안 된다. 재현해서
확인하면, 지적이 가리킨 것보다 좁고 구체적인 결함이 나온다.

## 3. 프로젝트 "있음/없음" 대신 증거의 세기

**문제.** 프로젝트가 존재하기만 하면 `project_weight = 0.5` 가 붙었다.
재현해보니 **아무것도 안 한 0% 짜리 빈 프로젝트가 우선순위를 400 →
200 으로 반토막** 냈다. "프로젝트를 만들어두기만 하면 그 스킬은 덜
급하다" 는 뜻이 되어버린다.

**정한 것.** 다섯 칸짜리 사다리 (커밋 `298a87d`).

```
started      0.10   만들기만 했다
in_progress  0.25   진행 중
completed    0.50   끝냈다
shown        0.70   끝냈고 + 보여줄 수 있다 (GitHub/데모/결과)
used         0.85   끝냈고 + 보여줄 수 있고 + 경험으로 썼다
```

**대가.** 계산이 복잡해졌다. 대신 두 앵커를 지켰다 — 완료=200,
완료+학습100%=120. 기존 감각을 깨지 않으면서 빈 프로젝트만 걸러낸다.

## 4. 수요의 분모를 하나로 모은다

**문제.** `Job`(옛 모델)과 `Opportunity`(새 모델)가 각자 분모를 세고
있었다. 같은 스킬이 화면에 따라 다른 비율로 보였다.

**추적해보니 원인은 다리 한 줄이었다.**

```python
if opportunity.opportunity_type != "job":
    return None
```

공모전·대외활동은 다리를 건너지 못해 한쪽에만 남았다.

**정한 것.** 분모를 `Opportunity` 하나로 통일하고 역방향 다리를 놓았다
(커밋 `591d955`, 마이그레이션 0013). 필드도 `job_count` → `demand_count`,
`total_jobs` → `total_demand` 로 바꿨다 — **이름이 거짓말을 하면
다음 사람이 같은 실수를 한다.**

**마이그레이션에서 하마터면 놓칠 뻔한 것.** 처음에는 다리를 안 건넌
Job 만 처리했다. 그런데 AWS 가 Job 에는 붙어 있고 짝이 되는
Opportunity 에는 없었다. 그대로 돌렸으면 **그 수요가 조용히
사라졌을 것이다.**

## 5. 수집기 대신 수동 입력을 먼저

**문제.** 공고를 어디서 가져올 것인가. API 연동(사람인·워크넷)과
수동 입력 중 골라야 했다.

**정한 것.** 수동 입력을 먼저 (커밋 `e0c4155`).

**이유.** 수집기를 먼저 만들면 **가짜 데이터 위에서 계산을 검증하게
된다.** 실제 공고를 손으로 넣어보는 편이 빠르고, 무엇보다 정직하다.

**실제로 그게 맞았다.** 대기업 · IT 기업 · 채용 플랫폼 공고 세 건을 넣자마자
mock 데이터로는 절대 안 나왔을 버그 셋이 나왔다.

1. **한글 조사.** `딥러닝을` 이 `딥러닝` 에 안 걸렸다. 단어 경계를
   지키느라 조사를 경계로 인정하지 않았다 → `PARTICLES` 목록 추가
2. **수동 입력의 기본 상태.** `discovered` 로 들어갔는데 마감 추적은
   `interested` 부터 시작한다. **D-1 짜리 공고를 직접 넣어도 오늘
   계획에 아무것도 안 올라왔다**
3. **마감 후보가 지원서만 봤다.** 지원서를 아직 안 만든 공고는
   마감이 내일이어도 계획에 못 들어갔다. "지원 준비" 와 "지원할지
   정하기" 는 다른 할 일이다

**대가.** 공고가 손으로 들어온다. 3건은 괜찮지만 20건이 되면 그 자체가
일이 된다. 공공 API(워크넷·고용24)가 다음 단계다.

**지킨 것.** 각 소스의 약관과 허용된 접근 방식을 확인한 뒤 연결한다.
모든 사이트를 스크래핑할 수 있다고 가정하지 않는다.

## 6. 한글을 다루려면 별칭이 필요하다

**문제.** 추출기는 스킬 이름을 글자 그대로 찾는다. 그래서 한글 공고에
`Machine Learning` 은 안 걸리고, 영문 공고에 `머신러닝` 은 안 걸린다.

**정한 것.** 스킬마다 쉼표로 구분된 별칭 (커밋 `d3bda91`).

```
Machine Learning  ← 머신러닝, ML
NLP               ← 자연어 처리, 자연어처리, Natural Language Processing
```

**한계는 남는다.** 추출기는 **"전공 목록"과 "요구 스킬"을 구분하지
못한다.** 실제로 났다 — 한 대기업 공고의 `모집 전공: ... 통계(이공) ...` 와
한 IT 기업 공고의 `(컴퓨터공학, 산업공학, 통계학 등) 전공` 에서 `Statistics` 를
요구 스킬로 잡았다. 손으로 떼어냈다.

이건 문자열 매칭의 근본 한계다. 문맥을 읽으려면 LLM 이 필요하다 —
어디에 쓸지는 **17장**에서 정했다.

## 7. 홈은 우주, 작업 화면은 평범하게

**문제.** 우주 테마를 앱 전체에 쓰면 일하는 화면이 읽기 어려워진다.
홈에만 쓰면 `ENTER` 를 누르는 순간 흰 화면이 나와 **텔레포트처럼**
느껴진다. 실제 피드백이 그랬다.

> "우주라는 그 배경 테마를... 너무 띡 띡"

**정한 것.** 작업 화면 상단에 **도착 띠**를 둔다. 우주에서 내려온 자리가
보여야 이동으로 읽힌다 (커밋 `2b11cf9`). 박스 테두리에는 남색 계열을
섞어 두 세계를 잇는다.

**같은 계열의 결정 하나 더.** 천체를 눌러 들어간 화면과 그 천체가
약속한 자리가 달랐다.

> "엔터친 곳과 들어가는 페이지가 같아야하지 않나"

→ 경로에 `section` 을 실어 화면 안 특정 자리까지 데려간다.

## 8. 홈에서 채운 요소는 하나뿐이다

**문제.** 북극성이 "오늘 뭘 하면 되지?" 인데, 홈에서 제일 큰 파란
버튼이 `ENTER`(지금 보고 있는 천체로 들어가기) 였다. 열자마자 눈이
닿는 곳이 북극성이 아니었다.

**정한 것.** TODAY 만 채우고 `ENTER` 는 테두리만 남긴다. 자리도
하단 카드에서 **궤도 바로 아래**로 올렸다 (커밋 `60d0e20`).

**왜 자리까지 옮겼나.** 1280×720 노트북에서 TODAY 가 접히는 선
아래(644px)로 내려갔다. **북극성이 스크롤 뒤에 있으면 안 된다.**

**옮기다가 헛짚은 기록.** 브라우저에서 궤도 높이만 인라인으로 바꿔
재보니 "줄이는 게 낫다" 는 결과가 나왔다. 그런데 천체 좌표는 JS 가
계산하므로 인라인 변경만으로는 재계산되지 않는다 — 원만 움직이고
천체는 그대로였다. `resize` 를 같이 발생시켜 다시 재니 **방향이
정반대**였다. 측정 도구를 의심하지 않으면 반대로 고친다.

## 9. 라우팅을 직접 만든다

**문제.** 화면 전환이 상태값이라 뒤로가기가 안 되고, "이 화면 봐줘"
라고 링크를 보낼 수도 없었다.

**정한 것.** react-router 를 넣지 않고 해시 라우팅을 직접 만들었다
(커밋 `7390417`, 약 40줄).

**이유.** 의존성이 늘지 않고, 정적 호스팅에 서버 설정이 필요 없다.
런타임 의존성을 `react` + `react-dom` 둘로 유지한다는 규칙을 지켰다.

**대가.** 중첩 라우트나 로더 같은 건 없다. 1인용 앱에 필요 없다.

## 10. 컨테이너 하나

**문제.** 화면과 API 를 나눌 것인가.

**정한 것.** 하나. FastAPI 가 빌드된 화면을 `backend/static` 에서 낸다.

**이유.** 둘로 나누면 CORS, 두 개의 URL, 두 번의 배포가 생긴다.
1인용 앱에 그럴 이유가 없다.

**대가로 겪은 것.** API 루트 `/` 가 화면보다 먼저 등록돼서 **배포본
첫 화면이 JSON 한 줄**이었다. `HAS_FRONTEND` 로 막았다.

## 11. 자격 증명 없이는 뜨지 않는다

**정한 것.** `CAREER_OS_ENV=production` 인데 자격 증명이 없으면
**앱이 아예 뜨지 않는다.**

**이유.** 기본 비밀번호를 두거나 조용히 인증을 끄면, 실수 한 번에
커리어 데이터 전체가 공개된다. 뜨지 않는 편이 낫다.

**실제로 배포가 그걸로 죽었고, 그게 맞는 동작이었다.** 다만 처음엔
"둘 중 뭐가 없다" 고만 말해서 왕복이 한 번 더 필요했다 → **무엇이
없는지** 이름을 대게 고쳤다.

**미들웨어에서 배운 것.** 미들웨어가 던지는 `HTTPException` 은
FastAPI 의 예외 핸들러를 거치지 않는다. 라우팅 바깥이라 그대로
터진다. `JSONResponse` 를 직접 돌려줘야 한다.

## 12. 배포본의 성격을 변수로 가른다

**문제.** 포트폴리오 데모에 비밀번호를 걸면, 링크를 연 사람이 README
로 돌아가 아이디를 옮겨 쳐야 한다. 거기서 대부분 이탈한다. 그렇다고
그냥 열면 링크를 아는 누구나 `/transfer/import` 한 번으로 데모를
비운다.

**정한 것.** 세 모드.

| 변수 | 인증 | 쓰기 | 쓰는 곳 |
|---|---|---|---|
| (없음) | 필요 | 가능 | 실사용 |
| `CAREER_OS_READ_ONLY=1` | 필요 | 차단 | 아는 사람에게만 |
| `CAREER_OS_PUBLIC_DEMO=1` | 없음 | 차단 | 포트폴리오 데모 |

**`PUBLIC_DEMO` 는 쓰기를 강제로 막는다.** "공개인데 쓰기 가능" 이라는
상태는 만들 수 없게 했다.

**변수를 나눈 이유.** `READ_ONLY` 를 재활용하면 이름이 하는 말과 하는
일이 달라진다. `PUBLIC_DEMO` 는 "인증을 없앤다" 는 뜻이고, 실사용
서비스에 실수로 들어가면 진짜 경력 기록이 그대로 공개된다.
**이름만 보고 무슨 일이 벌어지는지 알아야 한다.** 기동 로그도 모드를
적는다.

**메서드로 막지 경로 목록으로 막지 않는다.** 목록을 관리하면 새
라우터가 생길 때마다 빠뜨리고, 빠뜨린 쪽이 열린 채로 남는다.

## 13. 데이터는 API 로만 드나든다

**문제.** 배포본의 DB 는 볼륨 안의 SQLite 파일 하나다. 밖에서 만질 수
없다. 진짜 데이터를 넣을 방법도, **꺼낼 방법도** 없었다 — 볼륨을 한 번
잘못 지우면 그걸로 끝이었다.

**정한 것.** `/transfer/export` · `/transfer/import` (커밋 `f2d5baa`).

**엔티티마다 손으로 짜지 않았다.** 테이블이 19개에 연결 테이블이 6개고,
새 테이블이 생길 때마다 하나씩 빠뜨리게 된다. 메타데이터를 읽어 전부
덤프하고 **기본키를 살려서** 넣는다. 그래야 외래키와 연결 테이블이
저절로 맞는다.

**거부하는 것 셋.** 스키마 리비전이 다른 파일 / 모르는 테이블·컬럼 /
`confirm=REPLACE` 없는 불러오기.

**합치지 않고 대체한다.** 합치면 같은 ID 를 가진 다른 레코드가
부딪히고, 무엇이 남고 무엇이 덮였는지 아무도 모르게 된다.

**만들면서 잡은 것.** `transfer` 가 `models` 를 임포트하지 않아
metadata 가 비었고, **내보내기가 성공했다면서 빈 파일을 만들었다.**
API 로 부르면 `main.py` 가 모델을 먼저 임포트해서 멀쩡했고, 스크립트로
직접 부를 때만 그랬다. 백업 도구에서 이보다 나쁜 실패는 없다 —
백업이 있다고 믿게 된다.

## 14. 실제로 써봐야만 나오는 것들

이 프로젝트에서 가장 반복된 교훈이다. **배포하고 진짜 데이터를 넣고
직접 써보기 전까지는 안 보이는 결함이 따로 있다.**

| 증상 | 왜 안 보였나 |
|---|---|
| 빈 백업을 성공이라 보고 | API 로 부르면 멀쩡. 스크립트로만 재현 |
| 한글 아이디에 401 대신 500 | `compare_digest` 가 비-ASCII 를 거부. 한글을 넣어봐야 남 |
| 경력 데이터가 `.gitignore` 를 빠져나감 | 파일 이름을 하나 더 만들어봐야 남 (두 번 반복) |
| 좁은 화면에서 천체가 글자를 덮음 | 화면을 실제로 띄워야 남 |
| 유령 계획 항목 | 목업 지원서를 지워봐야 남 |
| `Study X for 0 minutes` | 종이책을 넣어봐야 남 |
| 공고 링크 없음 | 지원하러 가보려 해야 남 |
| 지운 목업이 배포본에서 되살아남 | 며칠 뒤 다시 올려보고 `replaced` 를 세어봐야 남 |

마지막 것은 원인이 화면이 아니라 **응답 필드 누락**이었다. 같은 종류가
여러 번 났다 — `ProjectResponse.skills`, `OpportunityResponse.skills`,
`DailyPlanTask.opportunity_id`, `match.source_url`.

**그래서 규칙을 하나 세웠다.**

> 필드를 하나씩 나열하지 말고 `model_dump()` 를 쓴다.
> 나열하면 스키마에 새 필드가 생겼을 때 조용히 누락된다.

## 17. LLM 은 판단하는 자리가 아니라 읽는 자리에 둔다

**문제.** "오늘 뭘 하면 되지?" 를 LLM 에게 물으면 그럴듯한 답이 나온다.
웹 검색까지 붙이면 더 그럴듯해진다. 그러면 이 앱이 하는 계산은 다
필요 없는 것 아닌가.

**정한 것.** 두 자리를 가른다.

| | 누가 하는가 | 왜 |
|---|---|---|
| **순위·오늘 계획** | 산수 | 근거를 댈 수 있어야 한다 |
| **글 읽기** | LLM | 문자열 매칭으로는 안 되는 일이다 |

**순위에 LLM 을 넣지 않는 이유.** 지금 `Machine Learning 400점 ·
수요 3/3` 은 셀 수 있는 것에서 나온다 — 공고 3건 중 3건이 요구,
레벨 0, 목표까지 4단계. LLM 에게 물으면 답은 나오지만 **근거를 댈 수
없다.** `Why this plan?` 화면이 성립하지 않고, 첫 번째 원칙(근거 없는
추천은 없다)이 깨진다. 대시보드로 돌아가는 것보다 나쁘다 — 대시보드는
적어도 틀린 판단을 하지는 않는다.

**LLM 이 실제로 필요한 자리.** 전부 이 프로젝트에서 실제로 부딪힌
문제들이다.

| 문제 | 지금 | LLM 이면 |
|---|---|---|
| `통계(이공)` 이 전공 목록인가 요구 스킬인가 | 구분 못 함 → 오탐, 손으로 뗌 | 문맥으로 구분 |
| 공고의 지원 자격(전공·졸업·어학) | 아예 안 읽음 | 구조화해서 추출 |
| 책 목차 → 학습 단계 | 손으로 입력 | 자동 |
| 경험 → 자소서 구조 | 글자 수만 도움 | 구조 제안 (내용은 여전히 사람이) |

**웹 검색은 대부분 필요 없다.** 무엇을 검색할 것인가. 공고는 API 로
받는 게 맞고(약관 문제도 있다), 학습 자료 추천은 이미 **하지 않기로
한 것**이다 — "이미 가진 것도 못 보고 있다". 실제 용도는 책 목차
가져오기 정도이고, 그건 검색이 아니라 URL 하나 읽기다.

**RAG 는 지금 규모에 과하다.** RAG 는 코퍼스가 컨텍스트에 안 들어갈 때
쓴다. 전체 데이터가 **JSON 86행, 31KB** 다. 공고 3건과 책 15권은
통째로 프롬프트에 넣고도 남는다. 인덱스를 만들면 부정확한 검색이 한 겹
더 끼어들 뿐이다. 공고가 수백 건 쌓이면 그때 다시 본다.

**이름은 그대로 Guide 다.** 하는 일이 정확히 그것이므로 Tutor 로 바꿀
이유가 없다.

**대가.** 문맥을 읽는 일이 늘어나면 비용과 지연이 생기고, 추출 결과가
틀릴 수 있다. 그래서 LLM 이 뽑은 것은 **제안으로 두고 사람이 확인한
뒤 저장한다** — 지금 손으로 떼어낸 `Statistics` 오탐처럼, 틀린 추출이
조용히 수요 계산에 들어가면 안 된다.

## 19. 이월에 수명을 준다

**문제.** 이월은 "어제 못 한 것을 그냥 버리지 않는다" 는 좋은 규칙이다.
그런데 이월은 계획의 앞자리를 차지하고, 하루는 세 칸뿐이다.

실제로 이렇게 됐다.

```
Machine Learning  400점  수요 3/3   ← 계획에 없음
AWS                 0점  수요 0/3   ← 계획의 전부 (사흘째 이월)
```

그 AWS 계획들은 **진짜 공고를 넣기 전에** 짜인 것이었다. 공고를 넣어
우선순위가 통째로 바뀌었는데도 이월은 다시 검사되지 않아서, 1위 스킬이
한 번도 계획에 올라오지 못했다. **"오늘 뭘 하면 되지?" 에 답하는
도구가 가장 중요한 일을 빼놓고 있었다.**

**정한 것.** 이월에 수명 3일을 준다. 넘긴 것은 후보에서 빠지고
**"이건 안 할 건가요?"** 로 물어본다.

**고르지 않은 것 둘.**

- *1위 스킬에 한 칸을 예약한다* — 이월이 줄지 않고 계속 쌓인다.
  증상만 가린다
- *그대로 둔다* — "안 끝낸 일이 셋이면 그걸 하는 게 맞다" 는 말도
  틀리지 않다. 다만 사흘째 미룬 일은 **사실 안 할 일일 가능성이
  높다.** 그걸 계획에 남겨두는 것은 "안 해도 되는 것을 말한다" 는
  원칙과 반대다

**조용히 버리지 않는다.** 계획에서 뺐다는 사실을 화면이 말하고,
**두 답이 다 가능해야 한다** — `그래도 할래요`(나이를 오늘로 되돌린다)
와 `치우기`(skip). 치우는 길만 있으면 그건 묻는 게 아니라 버리는 것이다.

**되살린 것도 다시 사흘을 넘기면 또 묻는다.** 한 번 봐줬다고 영구
면제는 아니다.

## 20. 배운 것이 우선순위에 반영되게 한다

**문제.** 회고를 만들면서 "이번 달에 레벨이 얼마나 올랐나" 를 세려다
알았다. `/skills` 에는 `POST` 와 `GET` 뿐이었다. **레벨을 바꿀 방법이
아예 없었다.**

이건 이력이 없는 것보다 훨씬 나빴다. 점수 공식이

```
priority = 시장수요 × 스킬격차 × 증거세기
스킬격차 = MAX_SKILL_LEVEL(4) − 현재레벨
```

인데 레벨이 만들 때 값에 영원히 머문다. 즉 **「핸즈온 머신러닝」 9장을
다 읽어도 Machine Learning 은 레벨 0 · 400점 그대로**다. 배운 것이
우선순위에 하나도 반영되지 않는다.

"오늘 뭘 하면 되지?" 에 답하는 도구가, 어제 한 일을 오늘 계산에
넣지 못하고 있었다.

**정한 것.**

- `PATCH /skills/{id}` — 레벨을 고칠 수 있게 한다. 상한은 스키마가
  막는다 (`ge=0, le=4`). 넘으면 격차가 음수가 되어 점수가 뒤집힌다
- `skill_level_events` — 변화를 기록으로 남긴다 (마이그레이션 0016).
  현재 값만 들고 있으면 "이번 달에 무엇이 늘었나" 를 셀 수 없다
- 화면 — Learning 의 "스킬별 우선순위" 줄에 0~4 버튼을 둔다.
  누르면 점수를 다시 **서버에서 받아온다**. 화면이 계산하면 두 곳에
  계산이 생긴다

**같은 값으로 다시 저장한 것은 변화가 아니다.** 기록하면 이력이
잡음이 된다.

**회고에서는 처음과 끝만 보여준다.** `0 → 1 → 2` 를 두 줄로 보이면
"두 번 올랐다" 로 읽힌다. 실제로 일어난 일은 "0에서 2가 되었다"
하나다. 제자리로 돌아온 것(`0 → 1 → 0`)은 변화가 아니다.

**소급하지 않는다.** 기록이 생기기 전의 변화는 알 수 없으므로 없는
것으로 둔다.

**곁들여 잡은 것.** 우선순위 응답에 `skill_id` 가 없었다. 이름만
주면 화면이 무엇을 고칠지 모른다 — 지금까지 나온 응답 필드 누락과
같은 종류다.

## 21. 달력은 한 장에 다 보이게 한다

**문제.** Calendar 화면은 요일 격자와 입력 폼뿐이었다. 하루짜리 일정은
격자에 안 뜨고(매주 반복처럼 보이면 거짓이라 뺐다), 공고 마감은
Opportunities 에 따로 있었다. "다음 주 목요일에 뭐가 있지?" 를 답할 수
없었고, 캡스톤·논문 마감처럼 공고가 아닌 마감은 넣을 곳이 없었다.
격자의 일정을 누르면 확인 없이 바로 지워지기도 했다.

**정한 것.**

- 한 달 격자(`GET /calendar/month`)에 매주 일정 · 하루 일정 · 지원서와
  공고 마감을 같이 놓는다. 날짜를 누르면 오른쪽에서 그날을 보고 고친다.
  시간 축이 필요하면 주 보기로 바꾼다.
- 일정 종류에 `deadline` 을, 일정에 `all_day` 를 더한다 (0018).
  **마감과 종일 일정은 빈 시간을 줄이지 않는다.** 마감은 그날 할 일이
  아니라 그날까지의 선이고, 종일 일정은 몇 시에 막히는지 모른다.
  빼면 그날 하루가 통째로 사라진다.
- 달력에 넣은 마감은 Today 의 D-day 띠에 뜨지만 **할 일로 만들지 않는다.**
  그날까지 무엇을 준비해야 하는지 앱은 모른다.
- 철회한 지원서의 마감은 달력에서도 뺀다. 남아 있으면 아직 할 일처럼 읽힌다.
- 삭제는 두 번 누른다. 매주 반복 일정은 "매주 전부 삭제" 라고 말한다.

## 22. Applications 는 "다음에 할 한 가지" 부터 보여준다

**문제.** 목록에는 상태 칩과 "열기" 뿐이라, 무엇을 할지는 지원서를 하나씩
열어 봐야 알았다. Workspace 머리에는 `preparing` 같은 원시값과 `87 MATCH`
처럼 근거 없는 숫자가 떠 있었고, 좁은 화면에서는 자소서가 분석 아래로
밀렸다. 저장하지 않은 글은 문항을 옮기면 사라졌다.

**정한 것.**

- 다음 행동은 서버(`GET /applications/board`)가 정한다. 상태 전이 규칙과
  같은 곳이어야 목록 · Workspace · 요약이 서로 다른 말을 하지 않는다.
  순서: 끝남 → 결과 기다림 → 마감 지남 → 문항 없음 → 안 쓴 문항 →
  제한의 절반보다 짧은 문항 → 상태 한 칸 옮기기 → 제출.
- 맨 위 요약의 다음 행동은 지원 전 지원서 중 마감이 가장 가까운 것.
  고를 근거가 없으면 비워 두고 "정보가 부족합니다" 라고 말한다.
- 매칭은 백분율 하나가 아니라 `요구 역량 N개 중 M개 보유` 로 보인다.
  보유 = 스킬 레벨 1 이상. 강조도 가중 %는 보조로만.
- 본문에서 등록된 스킬 이름을 하나도 못 찾으면 공고에 직접 연결한 스킬을
  근거로 쓰고, 그 사실을 한계에 적는다. 실제 공고가 "AI/Agent" 로 적혀
  "AI Agent" 를 못 찾았다.
- 상태 전이 409 사유를 한국어 라벨로 말한다. 화면은 그 문장을 그대로 보인다.
- 작성이 분석보다 먼저다. 좁은 화면은 요약 → 다음 행동 → 자소서 → 경험 → JD → 한계.
- 문항별 저장 전 글을 따로 들고 있고, 창을 닫거나 목록으로 가려 하면 묻는다.

**하지 않은 것.** 문장을 만들거나 줄이는 버튼. 공고에서 문항을 자동으로
읽어 오기(원문 링크만 연다). 강제 전이(force)를 화면에 노출하기.

**문서와 실제의 불일치 (고치기 전 기록).** FEATURES 14·15장은 "API만 ·
화면 없음", APPLICATIONS.md 는 "상태 전이 규칙 없음 · 자동 매칭 없음 ·
화면 전체 없음" 이라 적혀 있었지만 화면 · 전이 규칙 · 자동 매칭은 이미
있었다. 이번에 함께 고쳤다.

## 23. 모든 작업 화면이 같은 모양으로 말하고, Today 는 할 일 하나부터

전체 UI/UX 개선의 0 · 1단계 (방향 결정: 바탕색 유지 · 작업 화면 한국어 ·
단계별 확인).

**문제.**

- 로딩 · 오류 · 빈 상태가 화면마다 달랐다. Today 는 첫 로드가 실패하면
  `plan.available_minutes` 에서 화면이 깨졌고, 다시 시도할 길이 없었다.
- 공개 데모에서 모든 쓰기 버튼이 눌리고, 누른 뒤에 403 으로 막혔다.
- Today 에는 계산 용어와 원시값이 떠 있었다.
  - 영문 라벨: `TOTAL TIME`, `START TODAY`
  - 작업 종류가 영어 그대로: `opportunity`
  - 이유에 원시 점수: `(점수 87)`
- 완료를 누르면 무엇이 바뀌는지는 눌러 봐야 알았다.
- 시간 표기가 `2h 30m` 과 `2시간 30분` 으로 섞였다.

**정한 것.**

- 공통 컴포넌트 `components/ui.jsx` + `ui.css`:
  - 버튼(쓰기 버튼은 읽기 전용이면 미리 꺼짐), 로딩, 오류(다시 불러오기), 빈 상태(행동 버튼 포함)
  - 다음 행동 카드, 근거 패널(결론 먼저 · 숫자는 접기), 진행 막대, 배지, 두 번 눌러 확인, 알림
  - 표기는 `format.js` 하나로.
- 의미 색은 `:root` 에 더한다 — 행동 파랑 · 주의 호박 · 완료 초록 · 부족 빨강.
  바탕과 선은 기존 토큰 그대로.
- Today 맨 위는 세 가지 — 오늘 쓸 수 있는 시간 · 핵심 초점 · 가장 먼저 할 일(시작 버튼).
  작업은 3개까지 크게, 나머지는 지우지 않고 접는다.
- 작업마다 "선택 이유" 와 "완료하면" 을 쓴다. "완료하면" 은 서버가
  `complete_task` 와 같은 규칙으로 미리 센다 (`today.preview_completion`).
  자동으로 안 바뀌는 것(프로젝트 진행률 · 자료 챕터)은 안 바뀐다고 쓴다.
- 계획 이유는 원시 점수 대신 재료를 분모와 함께 쓴다 — "모아둔 기회 N건 중 M건이 요구 · 지금 레벨 L/4".
  이미 저장된 계획의 문구는 다음에 계획을 세울 때 바뀐다.
- 근거 화면(Why)과 한계 문장은 계산 용어(MARKET)가 아니라 화면 이름(시장 수요)으로,
  원시값(in_progress · official_doc · owned)은 한국어로.
- 사이드바 이름을 한국어로, 현재 화면에 `aria-current`.

**하지 않은 것.** Today 를 1~3개로 잘라 버리기(강도가 정한 개수는 그대로,
화면에서만 접는다). 체크 한 번에 프로젝트 진행률을 자동으로 올리기.

## 24. 학습은 다음 단계부터, 끝내면 무엇이 바뀌었는지

전체 UI/UX 개선 2단계 — 학습 · 학습 세션 · 내 자료.

**문제.**

- 학습 화면 맨 위가 "새 학습 경로" 폼이라, 들어올 때마다 무엇을 만들지부터 물었다.
- 영어 라벨이 곳곳에 있었다 — PRIMARY · NEXT STEP · START SESSION.
- 세션에는 "점수 87" 이 떴다.
- 단계를 끝내면 "반영되었습니다" 한 줄뿐이었다. 세션에서 끝낸 단계가
  오늘 계획에는 할 일로 남아 있었다.
- 목표를 적을 곳이 없었고, 자료를 단계에 연결하는 API 는 있는데 화면이 없었다.
- 내 자료는 불러오기에 실패하면 화면이 깨졌고, 챕터는 확인 없이 지워졌다.

**정한 것.**

- 학습 맨 위는 이어서 할 단계 하나(진행 중 → 남은 것이 있는 경로).
  경로가 없으면 "학습 경로 만들기" 와 "우선순위 1위 스킬로 만들기".
  만들기 폼은 버튼 뒤로 접는다.
- 완료 응답에 진행률 전 → 후 · 바뀐 것 목록 · 다음 단계를 담는다.
  - 오늘 계획에 같은 단계가 있으면 함께 완료로 표시한다.
  - 이미 끝낸 단계를 다시 누르면 새로 바뀐 것이 없다고 말한다.
- 세션에서 목표를 적고(단계 설명을 한 줄에 하나로), 같은 스킬의 자료를 단계에 연결한다.
- 자료 응답에 `linked_steps` — 어느 단계에서 쓰는지.
  학습 단계에 아직 안 쓰는 자료 수를 보여준다.
- 중요도는 핵심 · 보조 · 깊이 파기와 그 뜻. "지금 안 해도 되는 자료" 는
  개수와 이유를 펼쳐 볼 수 있게.
- 진행과 레벨 탭은 우선순위 점수 대신 "기회 N건 중 M건이 요구 · 학습 X%".
- 좁은 화면: 다음 단계 → 이번 세션 자료 → 경로 목록. 세션의 시작/완료 버튼은 아래에 붙는다.

**하지 않은 것.**

- 목표 체크를 서버에 저장하기. 여전히 이 브라우저에만 남는다.
- 자료 전체 삭제 버튼. 지금은 챕터만 지운다.

## 25. 프로젝트는 끝나는 순간 증거로, 경험은 어디에 쓰였는지까지

전체 UI/UX 개선 3단계 — 프로젝트 · 경험.

**하지 않은 것.** 프로젝트 "다음 작업" 칸 — 담을 모델이 없다. 지금은 목표일과 하루 시간으로

## 26. 공고는 붙여넣어 가져오고, 기회는 고르기 위해 보여준다

전체 UI/UX 개선 4단계 — 기회. 공고 붙여넣기(규칙 기반)를 함께 넣었다.

**문제.**

- 화면
  - Match 숫자에 단위와 분모가 없었다. 점수 구성도 /40 · /30 같은 최대값이 없었다.

  - 마감은 마감 단서(마감 · 접수기간 · ~ · 까지)가 있는 줄의 날짜만 본다.

  - 연도나 시각이 없으면 짐작한 값과 그 사실을 함께 말한다.
  - 상시 · 수시면 마감을 비운다.
  - 회사는 "회사명:" 같은 표기나 ㈜ · 주식회사가 있을 때만 채운다.

- 화면
  - 맨 위 "지원할지 정하기" — 검토 중 · 추천 이상 · 지원서 없음 · 마감 전 중
    마감이 가장 가까운 것.
  - 목록은 검토 중 / 보류 / 관심 없음 / 전체. 줄마다 점수/100 · D-day · 지원서 · 자격 확인.
  - 상세 순서: 고려할 이유 → 필요한 역량(✓ 보유 · ! 부족) → 자격 확인 →
    준비 비용 · 마감 → 점수 구성(최대값 함께, 접기) → 다음 행동.
  - 다음 행동: 지원서 만들기(있으면 열기) · 오늘 계획에 준비 추가 · 지금은 보류 · 관심 없음.

  - "지금은 아닌 것" 은 평가가 아니라 집중을 지키는 정리라고 말한다.

**하지 않은 것.**

- 링크를 열어 본문을 가져오기.
- AI 로 칸 채우기 — 규칙이 자주 놓치는 칸이 생기면 그때 붙인다.
- 자격 충족 여부 판정.

## 27. 내 자료는 서가처럼 — 가로 레일, 종류를 닮은 카드, HOT

**문제.** 자료 46개가 세로 카드로 길게 쌓여 있었다. 무엇을 보고 있고
무엇이 다음인지 스크롤해야 알았다. 책 · 영상 · 문서 · 실습이 같은 모양이라
훑어볼 수 없었다. 모든 자료의 상태가 `saved` 하나였다.

**정한 것.**

- 서가(언제 보는가)와 중요도(얼마나 중요한가)를 나눈다. 서가는 기존 `status` 칸의
  값으로 둔다 — `in_progress` 지금 학습 · `queued` 다음 학습 · `on_hold` 보류 ·
  `completed` 완료 · `saved` 분류 전. 마이그레이션은 없다.
- 사람이 정하지 않은 자료는 서버가 기록으로만 서가를 정하고 이유를 준다
  (챕터를 모두 끝냄 → 완료, 챕터를 일부 끝냄 · 진행 중 단계에 연결 → 지금 학습,
  안 끝낸 단계에 연결 → 다음 학습). 기록이 없으면 분류 전. 사람이 정하면 그것이 앞선다.
- 진행률은 챕터로 셀 수 있을 때만 준다 (예상 분 기준). 챕터가 없으면 "셀 수 없어요".
- HOT 1 · 2 · 3 — 최근 30일에 끝낸 챕터(×2)와 오늘 계획에서 완료한 자료 작업(×1).
  기록이 없으면 순위가 없다. 1위를 지어내지 않는다.
- 오늘 학습에 꺼내기(`POST /resources/{id}/add-to-plan`) — 다음 챕터를 오늘 계획
  작업으로 올리고 지금 학습으로 옮긴다. 이 자료를 쓰는 안 끝난 단계가 있으면 그
  학습 세션으로 가는 링크를 준다. 같은 날 두 번 누르면 이미 있다고 말한다.
- 화면: 검색(제목 · 종류 · 스킬 · 학습 경로 · 챕터 · 링크) · 종류 칩 · HOT 띠 ·
  레일(지금 · 다음 · 보류 · 분류 전, 완료는 접힘). 레일마다 3장과 조금 걸친 넷째 장,
  화살표 · 전체 보기. 카드: 영상은 16:9 썸네일(YouTube 대표 이미지) · 재생 버튼 ·
  길이, 책은 좁은 세로 표지, 문서는 흰 종이, 실습은 터미널. 카드를 누르면
  넓은 화면은 오른쪽 서랍, 좁은 화면은 아래 시트.
- 기존 등록 · 챕터 관리와 "지금 쓸 자료" 는 지우지 않고 아래에 접어 둔다.

**하지 않은 것.** 3D 책장 · 도서관 그림. 영상 재생 위치 추적(데이터가 없다 —
챕터 단위 진행만). 바탕색을 따뜻한 오프화이트로 바꾸기(2026-09-15 결정 유지).

## 28. 자격증 · 어학은 프로필에 — 번호 없이, 만료는 미리

  발급 기관 · 상태(보유 · 준비 중) · 취득일 · 만료일 · 메모.
  **자격번호 · 수험번호 칸은 없다.** 보내도 저장되지 않는다. 제출은 원본 증빙으로.
- 만료 180일 안이면 "만료 N일 전", 지나면 "만료됨". 만료일이 취득일보다 빠르면 거부.
- 경험 화면에 "자격증 · 어학" 카드 — 어학 / 직무 자격 두 칸, 추가 · 고치기 · 두 번 눌러 삭제.
- 기회 상세와 붙여넣기 미리보기의 자격 경고 옆에 "내 어학 · 내 직무 자격" 을
  나란히 둔다 (어학 경고 → 보유한 어학, 자격증 경고 → 보유한 직무 자격).
  준비 중인 것은 넣지 않는다. **충족 여부는 판단하지 않는다** — 공고마다 인정 시험이
  다르다(어떤 회사는 영어회화로 OPIc · 토익스피킹만 인정한다).

**하지 않은 것.** 증빙 PDF 업로드 · 보관. 점수를 공고 기준과 비교해 "충족" 판정.

## 29. 한눈에 보기는 상태를, 회고는 다음 달을 — 계획 대비 실행을 센다

**문제.** 한눈에 보기는 옛 대시보드 데이터(주간 계획 · 원시 우선순위 점수 · 공고
목록)를 영어 라벨로 늘어놓고 누를 곳이 없었다. 회고는 끝낸 것만 셌다 — 계획한 것과
나란히 놓지 않으면 "무엇을 바꿀지" 가 안 보인다. 홈의 오늘 카드는 "2개 · 75분" 처럼
개수만 보여 질문에 답하지 못했다. 캘린더 설정은 글자를 칠 때마다 저장됐다.

**정한 것.**

- `GET /overview` — 새로 판단하지 않고 각 서비스 값을 모은다. 목표 · 준비도(근거),
  이번 주 실행, 학습 · 프로젝트 · 증거 · 지원서 · 7일 안 마감 · 자격증. 칸마다 들어가는 길 하나.
- **실행률의 분모는 끝난 날의 계획이다.** 끝냄 + 넘김 + 못 함(지난 날 planned).
  오늘 아직 안 한 것은 분모에 넣지 않는다 — 하루가 끝나지 않았다.
- 회고에 `execution` · `postponed`(이월된 제목별 횟수) · `next_month`.
  다음 달 제안은 규칙 셋뿐이고 근거 숫자를 같이 준다 — 끝난 계획 5개 이상에서 실행률
  50% 미만 → 하루 상한 낮추기 / 같은 일이 3번 이상 이월 → 쪼개거나 빼기 /
  프로젝트 작업을 3개 이상, 끝낸 것만큼 못 끝냄 → 더 작게 나누기.
  **기록이 적으면 말하지 않는다.** 달을 바꾸면 이전 달 숫자를 먼저 치우고,
  오류가 나도 달 이동은 남긴다.
- 홈: 오늘 카드는 첫 할 일을 보인다(`today.first_task`). 행성은 영어 + 한국어, 수치
  라벨 · 근거 세기(높음 · 보통 · 낮음)는 한국어. 화살표는 궤도에 초점이 있을 때만.
  "CAREER AGENT" 장식 카드 자리는 한눈에 보기로 가는 링크.
- 캘린더 설정은 칸을 벗어날 때 한 번 저장한다. 저장 뒤 "이미 세운 오늘 계획은 오늘
  화면에서 다시 세워야 반영" 을 알린다 — 저절로 다시 짜지 않는다.
- 안내(Companion) 이름을 한국어로, 한눈에 보기 · 회고 역할 추가, 원시 점수 대신
  레벨과 "기회 N건 중 M건". 열면 입력 칸에 초점, Esc 로 닫기.

**하지 않은 것.** 캘린더 저장 시 오늘 계획 자동 재계산. 다음 달 제안을 LLM 으로.
주간 계획(`/weekly-plan`) 제거 — 한눈에 보기 아래 "참고용" 으로 접어 둔다.

## 30. 학습은 체크 항목 단위로 — 계획은 세션이 만들고, 기록은 앱이 한다

**문제.** 학습은 경로 → 단계("2주차 — 인기 기반 추천")까지만 있었다. 실제로 오늘 하는
일은 그 아래 한 줄("movie_stats 생성")인데 담을 곳이 없어서, 주차마다 다른 세션에
체크리스트 아티팩트를 만들어 달라고 했다. 그 아티팩트의 체크는 새로고침하면 사라지고,
아티팩트는 외부 서버를 부를 수 없어 Career OS 로 보낼 방법도 없다. 단계 설명의 줄을
"오늘의 목표" 로 보여주던 체크도 브라우저에만 남았다.

**정한 것.**

- `learning_checklist_items` (0020) — 단계 아래 항목. kind 는 task(체크, 진행률 분모) ·
  note(묶음 설명) · link(자료, http(s) 만).
- **붙여넣기 → 미리보기 → 고쳐서 저장.** `POST /checklists/parse` 는 아티팩트 HTML ·
  Markdown · 줄글에서 제목 · 묶음(h2 · `##`) · 항목(li · `- [ ]`) · 설명(`class*=note` · `>`) ·
  링크를 규칙으로 고른다. 저장하지 않고 링크를 열지 않는다. 스크립트 · 스타일 · 버튼은 읽지
  않는다. 표는 가져오지 않고 몇 줄 뺐는지 알린다. 체크 상태는 글에 적힌 것(`[x]`, `checked`)만.
  실제 2주차 파일에서 3묶음 18항목 · 설명 1 · 링크 3 을 읽었다.
- 경로에서 체크리스트 한 장으로 **새 단계** 를 만들거나(`/learning-paths/{id}/checklist-steps`),
  있는 단계에 이어 붙이거나 통째로 바꾼다(바꾸면 체크 기록도 사라진다고 먼저 말한다).
- 첫 체크에 단계가 시작 전 → 진행 중. **모두 체크해도 단계를 끝내지 않는다** — "모두
  체크했어요" 로 완료를 권할 뿐이고, 체크 안 한 채 완료하면 결과에 남은 개수를 적는다.
- 오늘 계획의 학습 카드에 "체크 3/18" 과 다음 항목 세 줄.
- 예전 목표 줄은 "목표 N줄 옮기기" 로 체크리스트가 된다.

**총괄 LLM 을 앱에 넣지 않은 이유.** 무엇을 할지(주차 체크리스트)는 Claude 세션이 잘
만든다. 앱에 LLM 을 넣으면 키 · 비용이 생기고, "했다고 봐도 되나" 를 모델이 판정하게
된다 — 근거 없는 판단이다. 그래서 역할을 나눈다: 계획은 세션, 기록 · 진행률 · 레벨 규칙은
앱. 레벨은 체크로 자동으로 오르지 않는다.

**하지 않은 것.** 루틴(매일 코테) — 다음 작업. 체크 항목별 예상 시간과 오늘 계획이 항목을
골라 시간을 채우는 것. 세션이 앱 API 를 직접 쓰는 연결(배포본 자격 증명을 세션에 줘야 한다).

## 31. 매일 하는 일은 시간을 먼저 떼고, 마감 있는 학습은 스킬 순위를 건너뛴다

**문제.** 오늘 계획이 담을 수 있는 건 학습 단계 · 자료 · 프로젝트 · 마감뿐이었다.
"프로그래머스 하루 3문제 30분" 같은 반복 일은 넣을 곳이 없었다. 학습 후보는
**우선순위 1위 스킬의 다음 단계 하나** 라서, 이번 주말 Tave 발표 주차도 급한 컴퓨터비전
스프린트도 스킬 순위가 낮으면 한 번도 오르지 않았다. 체크리스트가 있는 주차 단계를 오늘
계획에서 완료하면 하루 치 했을 뿐인데 단계 전체가 끝났다.

**정한 것.**

- `routines` · `routine_logs` (0021) — 제목 · 분 · 요일(월=0) · 하루 목표 개수와 단위 ·
  연결 경로. 하루 한 줄 기록(몇 개 했는지).
- **루틴은 시간을 먼저 뗀다. 강도의 칸 수는 쓰지 않는다.** 코테 30분 + rehab 30분이
  "보통" 세 칸 중 두 칸을 먹으면 학습이 밀려난다. 배치는 급한 마감 → 루틴 → 나머지.
- **루틴은 이월하지 않는다.** 어제 못 푼 3문제를 오늘 6문제로 만들지 않는다.
- 완료할 때 실제 개수를 적는다(비우면 목표만큼). 연결 경로가 있어도 단계는 끝내지 않는다.
- **목표는 저절로 오르지 않는다.** 지난 7일 중 할 차례였던 날이 5일 이상이고 그중 5일
  이상 목표를 채웠을 때만 "4문제로 올리기" 를 근거 문장과 함께 권한다. 루틴을 만들기
  전 날은 차례로 세지 않는다 — 만든 날 "이번 주 1일 중 0일" 이 떴다.
- `learning_steps.due_date` (0021). 단계 마감이나 경로 목표일이 14일 안이면 스킬 순위와
  무관하게 후보가 된다(하루 둘까지). 마감 있는 프로젝트와 섞어 가까운 순으로, 우선순위
  1위 스킬의 단계보다 앞에. 3일 안이면 루틴보다도 앞.
- 체크 안 한 항목이 남은 단계는 오늘 계획에서 완료해도 **진행 중으로 둔다.**
- 취미 프로젝트는 "커리어 증거 아님" 으로 두면 이미 후보에서 빠진다 — 새로 만들지 않았다.
- 루틴 카드는 캘린더(시간을 정하는 곳)에. 최근 7일 점 · 이번 주 N일 중 M일.

**하지 않은 것.** 목표 자동 인상. 과제 시간 추정(아직 모름). 수업 시간표 입력 —
캘린더 매주 일정으로 이미 된다.

## 32. 공고는 고용24 공채속보로 — 제목이 아니라 모집 부문으로 고른다

**문제.** 공고 수집이 제일 막혀 있었다. 사람인은 승인 대기, 고용24 는 개인회원에게
채용정보 목록 · 상세를 열어주지 않는다(2026-09-16 신청 화면 안내). 개인에게 열린 것은
공채속보 · 공채기업정보 · 채용행사뿐이다. 공개 명세도 없어서 승인받은 키로 호출 주소
패턴을 직접 확인했다 — `210L21` 이 공채속보(264건), `210L31` 이 공채기업정보, `210L11` 이 채용행사.

**정한 것.**

- `collectors/work24.py` — 공채속보 목록 → 상세(`210D21`). 상세에 모집 부문별 직무 설명 ·
  신입/경력 · 근무지 · 전형 단계가 온다. 설명은 그것만 이어 붙이고 출처는 "고용24".
  키가 있고 공개 데모가 아닐 때만 켜진다. 매일 08:00 자동화가 함께 돈다.
- **제목으로 고르지 않는다.** 264건 중 제목에 데이터 · AI 가 있는 것은 1건이었다.
- **짧은 말은 제목 · 부문 이름에서만.** 처음에는 "데이터" · "AI" 를 직무 설명 어디서든 찾아 35건이
  남았는데 절반이 "급여 데이터 관리" · "AI Tool 기반 비주얼" 같은 인사 · 영업 · 마케팅이었다.
  이제 강한 말(데이터 분석 · 데이터 엔지니어 · 빅데이터 · 머신러닝 · NLP · LLM …)은 어디서든,
  짧은 말(AI · 데이터 · Data · DX)은 제목이나 부문 이름에서만 센다. 둘 다 환경변수로 바꿀 수 있다.
- 테스트는 `.env` 의 진짜 키를 지우고 돈다. 자동화 테스트가 실제로 264건과 상세를 부르다 5분을 넘겼다.

## 33. 회고에 스스로 평가 한 칸, 학습에 스킬 추가

**문제.** 회고의 숫자는 전부 기록에서 센 것이라 "그래서 이번 달이 어땠나" 는 말하지 못한다.
스킬은 API 로만 만들 수 있어서 새로 배우는 것(PyTorch · LLM …)이 수요 · 우선순위에 들어가지 못했다.

**정한 것.**

- `monthly_reflections` (0022) — 한 달에 한 줄. 1~5점(비워도 됨) · 잘한 것 · 아쉬운 것 · 다음 달 초점.
  **앱이 계산하지 않고 적은 그대로 둔다.** 아직 오지 않은 달은 적을 수 없다. 회고의 "다음 달에 바꿀 것" 아래.
- 학습 › 진행 탭에 스킬 추가 — 이름 · 분류 · 레벨(기준 문구: 과목 이수 · A0 · 자격증 · 경험 연결) ·
  다른 이름. "목표 직무에도 넣기" 를 켜면 준비도 계산에 들어간다.
- 같은 스킬을 두 번 만들지 않는다 — 대소문자 · 띄어쓰기만 다르면 409. 둘로 쪼개지면 수요와 레벨이 나뉜다.

**하지 않은 것.** 평가 점수로 무언가를 자동 판정하기. 스킬 삭제 · 이름 바꾸기 화면.

## 34. 판단이 끝난 기회는 보관함으로, 학습 단계는 다른 세션에 넘길 수 있게

**문제.** 기회 화면의 칸을 기회 상태(보류 · 관심 없음)로만 나눴다. 지원서를 철회한 공고가
검토 중 목록에 "오늘 마감 · 지금 할 만해요" 로 남았고, 이미 지원한 공고도 검토 목록에
섞였다. 마감이 지난 공고도 버릴 곳이 없었다. 학습은 주차 체크리스트를 다른 세션이 만드는데,
그 세션에 트랙 맥락과 형식을 매번 손으로 설명해야 했다.

**정한 것.**

- `build_match` 가 `lane` · `archive_reason` 을 준다. 화면이 상태 · 지원서 · 마감을 따로 조합하지 않는다.
  보관함(직접 닫음 · 지원서 철회/불합격/합격 · 마감 지남) → 지원 중(진행 중인 지원서) → 보류 ·
  관심 없음 → 검토 중. 보관함에는 "지금 할 만해요" 를 붙이지 않는다.
- 보관함에서 직접 닫은 것만 되돌린다(마감 지남 · 철회는 되돌려도 다시 온다). 완전히 삭제는 두 번
  눌러야 하고, 지원서가 달린 기회는 지원 기록 때문에 지금처럼 거절된다.
- 학습 단계에 "다른 세션에 넘길 프롬프트 복사" — `GET /learning-steps/{id}/handoff`. 경로 설명 ·
  이번 단계 · 마감 · 끝낸 단계 · 남은 체크 항목 · 자료 링크 · 붙여넣기 형식을 저장된 그대로 옮기고,
  없는 칸은 "없음" 이라고 쓴다. 형식 약속은 `docs/CHECKLIST_FORMAT.md`.

**하지 않은 것.** 마감 지난 기회 자동 삭제. 세션이 Career OS 에 직접 쓰는 연결.

## 35. 채용 행사는 가는 날로 — 수도권 박람회만, 담당자 연락처는 옮기지 않는다

**문제.** 고용24 채용행사(`210L11`)는 1,854건인데 앞으로 열리는 것은 37건, 수도권은 16건이었고 그
대부분이 조리사 · 어린이집 · 호텔 현장면접이었다. 행사는 지원하는 공고가 아니라 가는 날인데, 기회의
종류가 채용 · 공모전 · 대외활동뿐이라 넣으면 "공고 마감 · 지원할지 정하기" 로 읽혔다. 기회 목록 "전체"
에서는 종류가 글자로만 구분돼 한눈에 안 들어왔다. 학습 경로 설명은 고칠 화면이 아예 없었다.

**정한 것.**

- `collectors/work24_events.py` — 목록 전체에서 앞으로 열리고 · 서울 · 경기 · 인천이고 · 이름에
  박람회 · 잡페스타 · 청년 · IT · 데이터 · 전산 같은 말이 있는 행사만, 기업 참가 신청 공고는 뺀다(모두
  환경변수로 바꿀 수 있다). 고른 것만 상세(`eventNo` + `areaCd`)로 일시 · 장소 · 내용을 붙인다.
  2026-09-16 실제로 4건이 남았다.
- **상세의 담당자 이름 · 전화 · 팩스 · 이메일은 읽지도 저장하지도 않는다.** 원문 링크가 응답에 없어서
  주소를 지어내지 않는다.
- 새 종류 `job_event` (채용 행사). 마감일은 행사 마지막 날. 지나면 보관함 "지난 행사". 요구 스킬이 없어
  점수가 늘 낮으므로 검토 중에서는 "고려해 볼 만해요" 로 두고 사람이 정한다. 오늘 계획은 "참석할지 정하기",
  달력은 "채용 행사".
- 기회 목록 행에 종류 칩과 연한 배경 · 왼쪽 선 — 채용 파랑 · 공모전 주황 · 대외활동 초록 · 채용 행사 보라.
- 학습 경로 카드에 설명 · 목표일 보기와 고치기. 설명은 다른 세션에 넘길 프롬프트의 "이 트랙" 이 된다.
