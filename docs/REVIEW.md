# Career OS — 외부 검토용 안내

> 이 문서는 **코드를 실행하지 않고도 판단할 수 있게** 쓴 것이다.
> 앱은 Dockerfile 하나로 배포된다 — 공개 데모(읽기 전용 · 지어낸 데이터)와
> 실사용(Basic Auth) 두 벌이다.
>
> 저장소: https://github.com/nocked115/career-os
> 화면 시안: https://claude.ai/code/artifact/936eecf1-4671-4e43-8a2e-25652366417f

## 1. 이게 뭔가

대학생 한 명이 자기 커리어를 관리하려고 만드는 **1인용 시스템**이다.
로그인 화면도 사용자 목록도 없다. 배포본 접근만 Basic Auth 로 막는다.

**북극성 질문 하나: "오늘 뭘 하면 되지?"**

쌓여 있는 것들 — 산 책, 저장해둔 유튜브, 하다 만 프로젝트, 열어둔 공고 —
을 놓고 **오늘 할 일**을 정해주는 것이 이 앱이 하는 전부다.
개수는 강도가 정하고, 화면은 앞의 세 개만 크게 보이고 나머지는 접는다.
한 달이 끝나면 **계획한 것과 실제로 한 것을 나란히** 놓고 다음 달에 바꿀 것을 말한다.

### 하지 않는 것

| | 왜 |
|---|---|
| 새 학습 자료 추천 | 이미 가진 것도 못 보고 있다. 더 주면 부담만 는다 |
| 자기소개서 대신 쓰기 | 지어낸 경험이 들어간다. 구조와 글자 수만 돕는다 |
| 학교 시간표 가져오기 | 형식과 학교마다 다른 규칙에 묶인다. 직접 넣는다 |
| 커리어 완료율 표시 | 커리어에 완료율이란 게 없다. 근거를 댈 수 없다 |

## 2. 원칙 셋 — 이걸 기준으로 봐주면 좋겠다

### 원칙 1 · 근거 없는 추천은 없다

무언가를 하라고 하면 **왜 지금 그것인지**가 항상 옆에 붙는다.
설명할 수 없으면 화면에 올리지 않는다.

```
❌  EC2 Fundamentals                      30 min
✅  EC2 Fundamentals                      30 min
    AWS 가 우선순위 1위 — 등록 공고 1건 중 1건이 요구
```

파생 규칙 하나: **퍼센트는 분모 없이 쓰지 않는다.**
공고가 1건일 때도 100% 는 100% 다. `100%` 라고만 쓰면 화면이 거짓말을 한다.

### 원칙 2 · 안 해도 되는 것을 말한다

추천 서비스는 계속 뭘 더 보라고 한다. 이 앱은 반대다.

```
지금 필요한 것 · 5개
  ...
┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄
영상 3개 · 논문 1개
지금은 볼 필요 없습니다. 필요해지면 다시 올라옵니다.
```

**치운 것을 개수와 이유까지 보여주는 것까지가 선별이다.**
조용히 감추면 그건 선별이 아니라 필터다.

### 원칙 3 · 홈은 특별하게, 작업 화면은 편하게

홈은 어두운 "커리어 우주"(궤도 위 천체 = 영역),
작업 화면은 밝고 읽기 쉬운 카드.
작업 화면의 이름과 라벨은 한국어, 홈 행성 이름만 영어 + 한국어(`LEARNING · 학습 · 내 자료`).

## 3. 아키텍처

```
frontend (React 19 + Vite, 런타임 의존성 react/react-dom 둘뿐)
    │  fetch
    ▼
FastAPI  routers/     ← HTTP 만. 계산하지 않는다
    │
    ▼
         services/    ← 판단이 사는 곳. 계산은 여기 한 번만
    │
    ▼
SQLAlchemy → SQLite   (Alembic 이 스키마 소유, create_all 안 씀)
```

| | 규모 |
|---|---|
| 백엔드 | 약 14,900줄 · 59파일 |
| 테스트 | 42파일 · **540개 수집** |
| 프론트 | 약 21,800줄 (js · jsx · css) |
| 엔드포인트 | 약 155개 (routers 127 + main.py 28) |

### services/ — 판단 로직

| 파일 | 하는 일 |
|---|---|
| `priority.py` | 학습 우선순위. **모든 화면이 이 하나를 쓴다** |
| `today.py` | 오늘 계획 생성 (강도·마감·이월) |
| `library.py` | 자료 선별. 고른 것 + **치운 것** |
| `opportunity.py` | 공고 매칭 점수 (관련성 40 / 준비도 30 / 포트폴리오 15 / 마감 15) |
| `why.py` | 판단 근거를 한곳에 모은다. **새로 계산하지 않는다** |
| `universe.py` | 홈 데이터. 역시 조합만 |
| `calendar.py` | 오늘 몇 분 비었나 |
| `evidence.py` · `proof.py` | 증거 집계, 프로젝트→경험 |
| `jd.py` · `application.py` | 공고 분석, 지원 상태 전이 |
| `application_board.py` | 지원서마다 다음에 할 한 가지 |
| `posting_parser.py` | 붙여넣은 공고 글에서 칸 찾기 (규칙 기반, 링크를 열지 않음, 저장 안 함) |
| `certificates.py` | 자격증 · 어학. 번호는 담지 않고 만료를 미리 말한다 |
| `overview.py` | 한눈에 보기. 각 서비스 값을 모을 뿐 **새로 판단하지 않는다** |
| `review.py` | 월간 회고. 끝낸 것 + 계획 대비 실행 + 이월 + 다음 달 제안 |

**중요한 규칙: 계산은 한 곳에만 있다.**
전에 우선순위 계산이 4곳에 복붙돼 있었고 값이 서로 달랐다.

## 4. 핵심 판단 로직 — 실제 계산식

### 학습 우선순위 (`services/priority.py`)

```
market_percentage = round(요구하는 기회 수 / 모아둔 기회 수 × 100)
                    # 공고 · 인턴 · 공모전 · 대외활동을 모두 센다
                    # 채용 시장 전체가 아니라 "내가 모아둔 것" 이다
skill_gap         = max(0, 4 - 내 레벨)

evidence_strength = 프로젝트가 어디까지 갔는지 (0.10 ~ 0.85)
                    학습 진행률과 겹치는 만큼 빼고 합침
evidence_weight   = max(0.15, 1.0 - evidence_strength)

target_weight     = 1.0 (목표 스킬이거나 목표 없음) / 0.6 (목표와 무관)

priority_score    = round(market_percentage × skill_gap
                          × evidence_weight × target_weight)
```

**증거 가중치가 점수를 낮추는 방향인 게 핵심이다.**
이미 프로젝트로 증명 중인 스킬은 덜 급하다.

### 오늘 계획 예산 (`services/calendar.py`)

```
활동 시간대 09:00–22:00        780분   ← 사용자가 정함
− 일정 (겹침은 한 번만)         420분
= 빈 시간                      360분
  하루 상한                    180분   ← 사용자가 정함
→ 오늘 제안                    180분
```

**빈 시간을 그대로 쓰지 않는다.**
9시간이 비어도 9시간 공부하지 않기 때문이다.

### 준비도 (`services/universe.py`)

```
목표 직무 스킬들의 (레벨 / 4) 평균 × 100
```

화면에 `50%` 만 띄우지 않고 `Data / AI 스킬 3개 평균 숙련도` 를 같이 쓴다.

### 회고 — 계획 대비 실행 (`services/review.py`)

```
실행률 = 끝냄 / (끝냄 + 넘김 + 못 함)
         못 함 = 지난 날짜인데 아직 planned
         오늘 이후 아직 안 한 것은 분모에 넣지 않는다 — 하루가 끝나지 않았다
이월    = 이월돼 들어온 태스크를 제목별로 센 횟수 (상위 5개)
```

다음 달 제안은 **규칙 셋뿐**이고 근거 숫자를 같이 준다.

```
끝난 계획 5개 이상 · 실행률 50% 미만           → 하루 계획(상한)을 줄여 보세요
같은 일이 3번 이상 이월                         → 쪼개거나 계획에서 빼 보세요
프로젝트 작업을 3개 이상, 끝낸 것만큼 못 끝냄    → 더 작게 나눠 보세요
```

기록이 문턱보다 적으면 말하지 않는다. 계획 기록이 아예 없으면
"오늘 계획을 세우면 회고가 쌓여요" 하나만 준다.

## 6. 내가 아는 약점 — 숨기면 검토가 의미 없다

### 치명적이지는 않지만 확실한 것

1. **데이터가 거의 다 가짜다.**
   공고 1건이 `Mock Data Company`, 기회 3건 중 2건이 Mock,
   라이브러리에 `string` 이라는 API 테스트 잔재가 있다.
   **화면의 모든 숫자가 이 가짜 입력에서 나온다.** 계산은 맞지만 재료가 없다.

2. ~~라우팅이 없다~~ — 고쳤다. 해시 라우터(`frontend/src/router.js`)를 직접 뒀다.
   뒤로가기·링크 공유가 된다. 런타임 의존성을 늘리지 않으려고
   react-router 는 쓰지 않았고, 중첩 라우트·스크롤 복원은 없다.

3. ~~`Job` 과 `Opportunity` 가 다른 모수를 쓴다~~ — 고쳤다.
   원인은 브리지가 `job` 타입만 넘긴 것이었다(공모전·대외활동이 빠졌다).
   양방향 브리지를 놓고 모수를 `Opportunity` 하나로 모았다.
   `Why this plan?` 의 중복 칸도 하나로 합쳤다 (9종 → 8종).
   `Job` 테이블은 레거시 호환용으로만 남는다.

4. **LLM 이 없다.** Agent 는 키워드로 의도를 갈라 저장된 데이터를 꺼낼 뿐이다.
   전에는 `Learning Tutor` 라고 부르면서 "개념 설명은 못 합니다" 를
   같이 적었는데, 외부 검토에서 "그러면 Tutor 가 아닌데?" 를 지적받아
   이름을 실제 능력에 맞췄다 (`Learning Guide`, 지금 화면 표기는 "학습 안내").
   개념 설명이 가능해지면 그때 Tutor 로 올린다.
   회고의 다음 달 제안도 LLM 이 아니라 규칙 셋이다.

5. ~~`MARKET SIGNALS` 에 분모가 없다~~ — 고쳤다. `2 / 3` 이 먼저 오고
   퍼센트가 보조로 붙는다.

6. **주간 누적 시간은 계획으로 한 일만 센다.**
   계획 밖에서 공부한 건 안 잡힌다. 화면에 그렇게 적어뒀지만
   숫자가 실제보다 작게 나온다.

7. **아직 열린 구멍.**
   - `PATCH /applications/{id}` 는 상태 전이 규칙을 거치지 않는다. 규칙은 `/move` 에만 있다.
   - 오늘 계획의 자료 작업을 끝내도 챕터는 자동으로 체크되지 않는다.
   - 프로젝트 "다음 작업" 을 담을 모델이 없다.
   - 학습 목표 체크는 브라우저(localStorage)에만 남는다.
   - 사람인 수집원은 코드가 있지만 API 승인을 기다리는 중이다.
   - 프로젝트에는 완료 시각이 없어서 회고가 "이번 달에 끝낸 프로젝트" 를 세지 않는다
     (응답의 `not_tracked` 에 밝힌다).

### 반복해서 밟은 함정 (테스트로 막아둠)

- **응답에서 필드가 조용히 빠짐** — 네 번 반복됐다.
  `create_resource` 의 `importance`, `OpportunityUpdate` 의 `estimated_hours`,
  `create_project` 의 `results`, `ProjectResponse` 의 `skills`.
- **ALTER 로 붙는 컬럼에 `server_default` 누락** — 두 번. 마이그레이션이 중간에 죽었다.
- **Query 제약 누락** — `add-to-plan?minutes=-5` 가 200 을 냈다.

## 7. 검토자에게 부탁하는 것

코드를 다 읽지 않아도 좋다. 아래 질문에 답해주면 가장 도움이 된다.

### 제품

1. **"오늘 뭘 하면 되지?" 에 실제로 답하는 앱인가,
   아니면 결국 대시보드인가?** 원칙 1 이 화면에서 지켜지고 있나.
2. **"안 해도 되는 것을 말한다" 가 진짜 가치인가, 자기만족인가?**
   사용자가 "43개 안 봐도 됨" 을 보고 안심할까, 아니면 불안해할까.
3. **우주 홈이 필요한가?** 예쁘지만 클릭 한 번이 더 든다.
   요약 패널을 거치게 한 게 좋은 판단인가.
4. **1인용이라는 결정**이 이 제품의 한계를 만드는가, 아니면 지켜야 할 선인가.

### 설계

5. **우선순위 계산식**(4장)이 납득 가는가.
   특히 **증거가 있으면 점수를 낮추는 것**(`evidence_weight = max(0.15, 1 − 증거 강도)`)이
   맞는 방향인가. 반대여야 하지 않나?
6. **레거시 `Job`** 을 언제 지우는 게 맞나. 모수는 `Opportunity` 로 모았지만
   `/analytics/skills` · `/jobs/{id}/match` 가 아직 브리지된 `Job` 을 본다.
7. **LLM 없이 "Tutor" 라고 부르면서 한계를 적는 것**과
   **그 이름을 안 쓰는 것** 중 어느 쪽이 정직한가.

### 코드

8. `services/` 와 `routers/` 분리가 지켜지고 있나.
   계산이 라우터나 화면으로 샌 곳이 있나.
9. `today.py`(906줄) · `opportunity.py`(726줄) · `universe.py`(528줄) 이
   너무 큰가. 쪼갠다면 어디서.
10. 회고의 **실행률 분모**(끝난 날의 계획만)와 **다음 달 규칙 셋의 문턱**(5개 · 50% · 3번)이
    납득 가는가. 기록이 적으면 아무 말도 안 하는 게 맞나.
11. 테스트 540개가 **실제로 회귀를 잡는가**, 아니면 숫자만 채우는가.

## 9. 실행 방법 (검토자가 직접 돌려보려면)

```bash
# 백엔드
cd backend
python -m venv .venv
.venv/bin/pip install -r requirements.txt -r requirements-dev.txt
.venv/bin/alembic upgrade head
.venv/bin/uvicorn app.main:app --reload

# 테스트
.venv/bin/pytest -q

# 프론트 (다른 터미널)
cd frontend && npm install && npm run dev
```

숫자가 나온다. **빈 상태에서 화면이 어떻게 보이는지도 검토 대상이다.**
