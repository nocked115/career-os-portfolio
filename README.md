## 2. 어떻게 정하는가

"무엇이 부족한가"와 "그래서 오늘 뭘 하나"는 다른 질문이라 **두 층으로 나눴습니다.** 이 분리가 이 프로젝트의
핵심 설계이고, [실제 버그](#-프로젝트를-등록했더니-그-프로젝트가-오늘-계획에서-사라졌다) 때문에 나왔습니다.

```
  ① SKILL NEED  ─ 어떤 역량이 지금 부족한가
     시장 수요 × 격차 × 증거 부족 × 목표 관련성
                      │
                      ▼
  ② ACTION SELECTION ─ 그 부족함에 대해 오늘 무엇을 할 것인가
     마감 · 루틴 · 이월 · 마감 있는 학습 · 우선순위 학습 · 프로젝트 · 가용 시간
                      │
                      ▼
  ③ TODAY  ─ 3가지 · 120분 · 각각 고른 이유 한 줄
```

**① 어떤 역량이 부족한가**

```
market_percentage = 그 스킬을 요구하는 기회 수 / 모아 둔 기회 수 × 100
                    (채용 시장 전체가 아니라 "내가 모아 둔 것" — 분모를 속이지 않습니다)
skill_gap         = max(0, 4 − 내 레벨)
evidence_strength = 만들기로 함 0.10 · 만드는 중 0.25 · 완성 0.50 · 보여줄 수 있음 0.70 · 경험 0.85

priority_score    = market_percentage × skill_gap × max(0.15, 1 − evidence_strength) × target_weight
```

**증거가 점수를 낮추는 방향**이 핵심입니다. 이미 프로젝트로 증명 중인 스킬은 덜 급합니다. 반대로 설계하면
이미 잘하는 것만 계속 공부시키는 시스템이 됩니다.

**② 오늘 몇 분을 쓸 수 있는가**

```
활동 시간대 09:00–22:00   780분
− 수업 · 일정 (겹침 한 번)  420분
= 빈 시간                  360분
  하루 상한                180분
→ 오늘 제안                180분    "수업이 없는 시간"이 "공부할 수 있는 시간"은 아닙니다
```

**③ 그리고 닫힌 고리**

```
오늘 한 일  →  학습 단계 · 프로젝트 진행  →  증거 강도 변화  →  Skill Need 변화  →  내일 계획 변화
     ▲                                                                              │
     └──────────────────────────────────────────────────────────────────────────────┘
```

체크 하나가 다음 날 계획을 바꿉니다. 기록만 쌓이고 계획은 그대로인 도구가 되지 않으려고 이 고리를 먼저 닫았습니다.

## 3. 공고는 어디서 오는가

수집 방법과 판단 엔진을 갈라 두고, **출처마다 허용된 방식**으로 어댑터를 붙입니다.

```
 ① 공식 API           고용24 공채속보 · 채용행사 · 사람인(승인 시)
 ② 허용된 공개 소스     robots.txt 가 막지 않는 기업 채용 페이지 · 공공기관
 ③ 주소로 가져오기      사람이 고른 공고 한 건 — robots 를 먼저 읽고, 막혀 있으면 ④ 로
 ④ 붙여넣기            맞춤 공고 알림 메일 한 통 → 건별로 분리
        │
        ▼
   normalize()  →  job_fit(모집 부문 판단)  →  Opportunity  →  스킬 추출 · 점수 · 보관함
```

"스크래핑을 한다/안 한다"를 아키텍처로 두지 않았습니다. 사이트 내부 주소를 역으로 찾아 부르는 방식은 쓰지
않습니다 — 약관이 금지하고, 구조가 바뀌면 조용히 0건이 됩니다. **공고가 없는 건지 수집기가 깨진 건지 구분할
수 없는 게 가장 나쁩니다.**

### 데이터 품질이 진짜 문제였습니다

```
264건  공채속보 원본
  │  제목 키워드
  1건  ← "대졸 신입사원 모집" 안에 데이터 직무가 숨어 있었다
  │  상세의 모집 부문 · 직무 설명까지
 35건  ← 절반이 "급여 데이터 관리" 같은 인사 · 영업
  │  강한 말 / 짧은 말 2단 규칙
 19건
  │  모집 부문 단위 판단 (부문 이름 · 신입 여부 · 하는 일)
  8건  ← 영업 · 마케팅 · 생산 10건이 보관함으로, 이유 한 줄과 함께
```

마지막 단계가 필요했던 이유: 요즘은 마케팅 · 영업 공고 설명에도 "데이터 분석 기반 …"이 흔히 들어갑니다.
그 한 줄 때문에 **건강식품 온라인 영업이 88점**으로 목록 위에 올라왔습니다. 공고에서 뽑힌 스킬이 하나뿐이면
"요구 스킬을 100% 갖췄다"가 되던 점수식도 같이 고쳤습니다.

## 4. 무엇을 하지 않았나

| | 왜 |
|---|---|
| 앱 안에 LLM | 판단은 설명할 수 있어야 합니다. 계획 초안은 사람이 고른 AI 세션이 만들고, 앱은 그 결과를 받아 기록합니다 |
| 새 학습 자료 추천 | 이미 가진 것도 다 못 봤습니다. 더 주면 부담만 늘어납니다 |
| 커리어 완료율 % | 커리어에 완료율이란 게 없습니다. 근거를 댈 수 없는 숫자는 안 만듭니다 |
| 자기소개서 대신 쓰기 | 지어낸 경험이 들어갑니다. 구조와 글자 수만 돕습니다 |
| 분모 없는 퍼센트 | 모든 비율은 "12건 중 4건"처럼 분모와 함께 보여 줍니다 |

## 5. 실제로 부딪힌 문제 네 가지

#### ① 프로젝트를 등록했더니 그 프로젝트가 오늘 계획에서 사라졌다
60% 진행 중인 프로젝트를 스킬에 연결하자 다음 날 계획에서 빠졌습니다. 오늘 계획이 1위 스킬의 할 일만 봤는데,
프로젝트를 붙이면 증거가 생겨 그 스킬이 1위에서 내려갔기 때문입니다. → **"배울 필요"와 "끝낼 필요"를 분리**해,
프로젝트는 스킬 순위와 무관하게 후보가 되게 했습니다. 지금의 2층 구조가 여기서 나왔습니다.

#### ② 빈 프로젝트 하나가 우선순위를 반토막 냈다
아무것도 안 한 0% 프로젝트를 만들기만 해도 그 스킬 점수가 절반이 됐습니다. "있음/없음"으로 가중치를 곱했기
때문입니다. → **증거의 세기 5단계**로 바꾸고, 기존에 맞던 두 기준점은 유지했습니다.

#### ③ 토요일 발표가 어제 못 한 일에 밀려 계획에서 빠졌다
후보 순서가 "마감 → 이월 → 학습"이라 이월된 자료 두 개가 하루 칸을 먼저 차지했습니다. → 3일 안 마감인 학습 ·
프로젝트를 이월보다 앞에 두고 재현 테스트를 남겼습니다. **이월은 내일 해도 되지만 발표일은 옮길 수 없습니다.**

#### ④ 테스트가 5분을 넘기며 실제 API 를 부르고 있었다
앱이 시작할 때 `.env` 를 읽는데 거기에 진짜 인증키가 들어가자, 테스트가 실제로 공고 264건과 상세를
호출했습니다. → 모든 테스트에서 제공자 키를 지우는 autouse fixture 를 두고, 키가 필요한 테스트만 가짜 키를
받게 했습니다. 30초대로 돌아왔습니다.

> 계획이 낡았을 때 말해 주기, 잘못 누른 완료 되돌리기, "백업 성공"이라며 빈 파일을 만든 사고 등 나머지 기록은
> **[docs/DECISIONS.md](docs/DECISIONS.md)** 에 39장으로 남겨 두었습니다.

## 6. 구조

```
backend/                      FastAPI · SQLAlchemy 2 · Pydantic 2 · Alembic · SQLite
├─ app/routers/               HTTP 만. 계산하지 않습니다
├─ app/services/              모든 판단 — priority · today · opportunity · job_fit · review …
├─ app/collectors/            출처별 어댑터 (SOURCE_NAME · is_available · fetch · normalize)
└─ tests/                     658개

frontend/                     React 19 · Vite · 해시 라우터
└─ src/components/            런타임 의존성은 react · react-dom 둘뿐 (UI 프레임워크 없음)
```

- **계산은 서비스 한 곳에.** 라우터와 화면은 받은 숫자를 그대로 보여 주기만 합니다.
- **스키마는 Alembic 이 관리**하고 `create_all` 은 쓰지 않습니다. 마이그레이션 29개.
- 하루 한 번 스케줄러가 공고를 수집하고, 수집 뒤 직무 판단을 다시 돌립니다.

```bash
# 백엔드
cd backend && pip install -r requirements.txt && alembic upgrade head
uvicorn app.main:app --reload            # http://127.0.0.1:8000/docs

# 프런트
cd frontend && npm install && npm run dev
```
